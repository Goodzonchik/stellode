# Спецификация модели и правил

## 1. Архитектура хранения

- **Neo4j 5** (Bolt, язык запросов Cypher) — основная БД для графа зависимостей.

Версии сущностей представлены отдельными нодами; родители **`Component`**, **`Feature`** и **`Application`** связаны с версиями рёбрами, описанными ниже. **`Service` версионируемым родителем не является** (§2.1).

В будущем планируется использовать **PostgreSQL** как **опциональное** хранилище **обогащения нод графа**: описания, внешние ссылки и прочие метаданные, привязанные к стабильным `id` сущностей в графе. Каноническая модель графа и зависимости остаются в Neo4j.

### 1.1. Канон имён рёбер

Все типы рёбер в графе — **`SNAKE_CASE`**. Ниже — полный реестр.

| Ребро | Тип | Направление | Назначение |
| ----- | --- | ----------- | ---------- |
| `HAS_TEAM` | организационная | `Unit` → `Team` | Команда в юните |
| `OWNS` | организационная | `Unit` → `Application` | Владение приложением |
| `PROVIDES` | организационная | `Unit` → `Service` | Услуга юнита |
| `STAKEHOLDER` | организационная | `Unit` → `Feature` | Владение Feature |
| `MAINTAINS` | организационная | `Team` → `Component` | Команда сопровождает компонент |
| `AGGREGATES` | композиционная | `Service` → `Feature` | Состав услуги |
| `HAS_VERSION` | композиционная | родитель → `*Version` | Опубликованная версия сущности |
| `HAS_DRAFT` | композиционная | родитель → `*Version` | Черновик версии сущности |
| `INHERITED` | композиционная | `*Version` → `*Version` | Линейная история версий |
| `HAS_COMPONENT` | композиционная | `ApplicationVersion` → `ComponentVersion` | Состав релиза приложения; свойства: **`status ∈ { active, deprecated }`** (прикладной статус версии в данном релизе) |
| `USES_COMPONENT_VERSION` | композиционная | `FeatureVersion` → `ComponentVersion` | Компонент в составе фичи; свойства: **`id`** (UUID ребра), **`applicationId`** (родительский `Application`, в контексте которого фича использует версию) |
| `PINNED_TO_APPLICATION_VERSION` | композиционная | `FeatureVersion` → `ApplicationVersion` | Снимок релиза приложения на момент публикации FV (`draft → active`); без свойств; **подробнее в §6** |
| `DEPENDS_ON` | композиционная | `ComponentVersion` → `ComponentVersion` | Зависимость компонентов по контрактам |

## 2. Основные сущности

- **Unit** — бизнес-подразделение (управление разработки).
- **Team** — команда внутри юнита; владеет компонентами (`MAINTAINS`).
- **Application** — deployment-единица.
- **ApplicationVersion** — версия приложения; состав релиза через `HAS_COMPONENT` → `ComponentVersion`.
- **Service** — агрегат фич (услуга юнита).
- **Feature** — функционал в рамках юнита; одновременно может существовать **черновик** следующей версии и **опубликованная линия** (гибрид «намерение + доставленное»), см. §6.
- **FeatureVersion** — версия фичи; связь с компонентами через `USES_COMPONENT_VERSION` → `ComponentVersion`. Опубликованная версия в статусе **`active`** трактуется как **эпик** (обобщение доработки по компонентам), без требования lock-step с версиями компонентов (§6).
- **Component** — единица кода **или** управляемая внешняя зависимость: поле **`type ∈ { component, dependency }`** (в API может встречаться производный флаг `isDependency`). Классификация «разрабатываемый компонент / внешняя зависимость» задаётся **при создании один раз** и **не меняется** после: внешняя зависимость не «превращается» в разрабатываемый модуль и наоборот. Поле **`isPublic: boolean`** также задаётся при создании **один раз** и определяет, допускается ли использование контракта этого компонента в **cross-unit** и иных сценариях «внешней» экспозиции (в противоположность политике только внутренней сети юнита). Отдельные ноды `Dependency` / `DependencyVersion` в нормативной модели **не** вводятся — внешняя зависимость моделируется как `Component` с `type = dependency`. Компонент является набором классов, которые подвежены SRP.
- **ComponentVersion** — версия контракта компонента; признак публичности для cross-unit берётся с **родительского `Component`**, **`isPublic` версией не задаётся и не версионируется**.

### 2.1. `Service`, связь `AGGREGATES` и снятие фичи с услуги

- **`Service`** **не версионируется**. Нормативно **не** вводятся нода **`ServiceVersion`** и рёбра **`HAS_VERSION`** / **`HAS_DRAFT`** для `Service`. **`Service`** — **структурный агрегат** набора **`Feature`** (услуга юнита).
- Ребро **`AGGREGATES`** при выходе фичи из состава услуги **не удаляется физически**; на **данном** экземпляре ребра выставляется **`deleted: true`**.
- При **повторном** включении фичи в услугу создаётся **новое** ребро **`AGGREGATES`**; предыдущее с **`deleted: true`** **сохраняется** (история).
- **Инвариант:** для пары (`Service`, `Feature`) одновременно **не более одного** «активного» ребра **`AGGREGATES`** — у которого свойство **`deleted` отсутствует** или **не равно** `true`.
- **`Service.status`**: `active` | `archive` (по умолчанию при создании — `active`). **Архивация** не удаляет ноду: `POST …/archive` выставляет `archive`, `POST …/unarchive` возвращает `active` (идемпотентно, если уже `active`).
- **Мутации** состава (`AGGREGATES`), описания и прочих полей сервиса при `status = archive` **запрещены** (ответ API **409**).
- **Прод-срез (on-prod):** сервисы в статусе **`archive`** **не** участвуют в operational-диаграммах (unit / team / feature / integrations и др.) и **не** попадают в списки `services[]` impact в режиме **`on-prod`**. Старт impact от архивного сервиса в **`on-prod`** даёт пустой результат. Исключение: прямой просмотр **`GET /api/diagrams/service/:id`** для архивного сервиса остаётся доступным (read-only история состава).
- В режиме **`draft`** (`?projection=draft` на диаграмме услуги) архивный сервис может отображаться вместе с историей снятых `AGGREGATES` (`deleted: true`).

Логическая «связь двух фич / двух сервисов» **не** моделируется отдельными нодами: она **проецируется** из `USES_COMPONENT_VERSION`, ребра **`DEPENDS_ON`** между `ComponentVersion` и **атрибутов контекста** на `DEPENDS_ON` (сервисы, приложения, фичи/версии фич с обеих сторон) — см. §7.

## 3. Статусы и state machine версий

### 3.0.1. `ComponentVersion`: прод-семантика и статусы

**Отношение к прод-среде (эксплуатация):** версии со статусами **`active`** и **`deprecated`** считаются **находящимися на проде**; **`draft`** — **не на проде** (черновик новой версии / разработка); **`unactive`** — **сняты с прода** (история и анализ). Операционное отражение выката в графе — через релиз **`ApplicationVersion`** (§5.1) в сочетании с правилами §4.

**Прикладной vs глобальный статус.** Одна `ComponentVersion` может одновременно входить в `current`-состав **нескольких** приложений с **разным** прикладным статусом на ребре **`HAS_COMPONENT.status`**: в приложении A — `active`, в приложении B — `deprecated`. Глобальный `ComponentVersion.status` **хранится** на ноде, но **является производным** от рёбер `HAS_COMPONENT` у всех `ApplicationVersion` со статусом `current`:

- **`draft`** — версия ещё не опубликована (нет факта деплоя через релиз); производное правило к ней не применяется, пока статус `draft`.
- **`active`** — хотя бы в одном `current` существует ребро `HAS_COMPONENT` со `status = active`.
- **`deprecated`** — в `current` приложениях остались только рёбра со `status = deprecated` (нет ни одного `active`).
- **`unactive`** — версии нет ни в одном `current` (все рёбра `HAS_COMPONENT` только у `previous` или отсутствуют).

Ручного перевода глобального статуса `ComponentVersion` в API **нет**: смена статуса происходит только при релизе/откате приложения (§5) с последующим пересчётом.

| Статус | Смысл |
| ------ | ----- |
| `draft` | Проектирование и разработка; **не на проде**; новая `draft` создаётся от версии-базы по правилам §4. |
| `active` | Хотя бы в одном приложении на проде как актуальная линия (`HAS_COMPONENT.status = active`); **на проде**. У родителя **допускается несколько** глобально `active` версий (разные приложения). |
| `deprecated` | **На проде** хотя бы в одном приложении только как устаревшая линия (`HAS_COMPONENT.status = deprecated`); рекомендуется миграция. |
| `unactive` | **Снята с прода** во всех приложениях; только история и анализ; **новые** интеграции на эту версию не создаются.|

### 3.0.2. `FeatureVersion`: эпик и гибрид с черновиком

Используются **те же имена** статусов (`draft` / `active` / `deprecated` / `unactive`), но смысл на уровне **фичи** отличается от компонентного:

- У **`Feature`** одновременно допустимы **`HAS_DRAFT`** и опубликованные версии — **гибрид** «желаемые изменения (черновик) + доставленная линия».
- **`FeatureVersion` в статусе `active`** — **эпик**: обобщение доработки по набору компонентов; **не требуется** жёсткий lock-step номеров или единого среза с `ComponentVersion` (подробно §6).
- Для управления публикацией фичи используются дополнительные поля версии:
  - **`canAutoActive: boolean`** (по умолчанию `false`) — разрешение автоматического перехода `draft -> active` при выполнении критерия готовности (§6);
  - **`readyToProduction: boolean`** — **вычисляемый** признак готовности к публикации (не является частью state machine статусов).

| Статус | Смысл |
| ------ | ----- |
| `draft` | Черновик версии функционала: **желаемые изменения**, состав и связи `USES_COMPONENT_VERSION` (§6). |
| `active` | Текущая опубликованная линия фичи (**эпик**); у родителя только одна `active` среди опубликованных. |
| `deprecated` | Опубликованная линия в переходном состоянии; переходы — по §3.1 и правилам продукта. |
| `unactive` | История; **новые** связи на эту версию не создаются.|

**Бизнес-смысл статуса.** Статус `FeatureVersion` отражает состояние самого функционала как бизнес-намерения (черновик / опубликованный эпик / история). Смена этого статуса фиксирует только жизненный цикл фичи: она **не** пересчитывает прод-статусы `ComponentVersion` и **не** является релизом приложения (в отличие от §5).

### 3.0.3. `ApplicationVersion`

Черновика (`draft`) **нет**. Статусы строковые, для согласованности с остальной моделью версий:

| Статус | Смысл |
| ------ | ----- |
| `current` | Текущий прод-релиз приложения (у `Application` ровно одна такая версия). |
| `previous` | Любой выпущенный релиз приложения, который **не является** текущим (история). |

История релизов выстраивается ребром **`INHERITED`** между `ApplicationVersion` (линейная цепочка).

### 3.1. Правила переходов

Ниже — для **`ComponentVersion`** и **`FeatureVersion`** (статусы `draft` / `active` / `deprecated` / `unactive`). Для **`ApplicationVersion`** переходы **`current` / `previous`** — в §5.

- Допустим переход **`active → unactive`** без обязательного промежуточного `deprecated` (например единственный релиз БД/фронта).
- Переходы в **`deprecated`** и **`unactive`** **не блокируют** сохранение: перед подтверждением показывается **обязательное предупреждение**; событие **логируется** (см. также audit).
- При переходе **`active → unactive`** (и при необходимости при других деградирующих переходах): если у версии есть **потребители** (исходящие от других сущностей/версий связи использования или `DEPENDS_ON` на эту `ComponentVersion`), показывается **обязательное предупреждение/уведомление** с перечнем затронутых потребителей.

### 3.2. Удаление

- **`unactive`** и опубликованные версии трактуются как **soft delete** с точки зрения жизненного цикла.
- **Физически** удалять можно **только** ноду версии в статусе **`draft`** и **без зависимых связей** (нет рёбер кроме допустимых к родителю и `INHERITED` к предыдущей версии — как в операционных правилах API).
- Для **`FeatureVersion(draft)`**: исходящие рёбра **`USES_COMPONENT_VERSION`** **не** считаются блокирующими и снимаются каскадом при удалении ноды **только если нет других блокирующих связей**; иначе удаление отклоняется, состав USES не меняется. Перед удалением ноды также удаляются рёбра **`DEPENDS_ON`**, у которых в контексте `consumerFeatureVersionId` равен удаляемому draft.
- При попытке физически удалить версию и наличии блокирующих связей система возвращает структурированное описание блокировок:
  - `relationType`: тип связи (например `DEPENDS_ON`, `HAS_COMPONENT`, `PINNED_TO_APPLICATION_VERSION`, …)
  - `direction`: `incoming` или `outgoing` (относительно удаляемой версии)
  - `targetKind`: тип целевой ноды (лейбл)
  - `targetName`: имя/идентификатор для отображения пользователю
- Допускается дополнительно возвращать агрегированную сводку по типам связей.

## 3.3. Правила редактирования (immutability)

### 3.3.1. Родительские сущности

- Для **`Application`**, **`Service`**, **`Feature`** допускается редактировать любые поля, **кроме** **`name`**.
- Для **`Component`** допускается редактировать любые поля, **кроме** **`name`**, **`isPublic`** и классификации «разрабатываемый компонент / внешняя зависимость» (т.е. **`type`** и его эквиваленты, например `isDependency`); эти поля задаются при создании и **не** меняются после (смысл **`type`** — §2, `isPublic` — §2, cross-unit — §8).
- `name` задаётся при создании; после создания **не редактируется** (см. также §8.1).

### 3.3.2. Версии сущностей

- Для **`ComponentVersion`** в статусе **`draft`**: редактируются поля версии **`description`**. Исходящие `DEPENDS_ON` смыслово принадлежат контексту `FeatureVersion` (§6, §7.2) и **не** редактируются как состав CV.
- Для **`FeatureVersion`** в статусе **`draft`**: редактируются **все** поля версии (включая `canAutoActive`, `description`), **состав `USES_COMPONENT_VERSION`**, а также **исходящие `DEPENDS_ON`** с `consumerFeatureVersionId` = этот draft (создание и физическое удаление копии ребра; исторические рёбра других FV не меняются).
- В статусах **`active` / `deprecated` / `unactive`** для обоих типов допускается редактировать только **дополнительную информацию**: сейчас — только `description`.
- Для **`ApplicationVersion`**: допускается редактировать **только** атрибут **`version`** у версии со статусом **`current`** (операция Rename, §5.4). Поля **`versionNumber`**, состав **`HAS_COMPONENT`** и статус **`current` / `previous`** через rename **не** меняются. Для статуса **`previous`** редактирование запрещено.

## 4. Версии компонента (`Component` / `ComponentVersion`)

- У компонента **ровно одна** `draft` одновременно; пока есть `draft`, новую `draft` не создаём.
- У компонента **допускается несколько** глобально `active` версий (разные приложения держат разные линии); инвариант «одна `active`» действует **только внутри состава одного** `ApplicationVersion` (§5.1).
- Цепочка версий **линейная**: `INHERITED`, **без ветвления**.
- При создании нового `Component` автоматически создаётся первая `ComponentVersion` со статусом `draft` (без `INHERITED`, так как предыдущей версии нет).
- Новая `draft` создаётся с `INHERITED` от **версии-базы**: версия с максимальным `versionNumber` среди статусов **`active`** и **`deprecated`**; если таких нет — версия с максимальным `versionNumber` среди всех опубликованных (включая `unactive`).
- При создании новой `draft` копируется поле **`description`** с версии-базы; поле **`version`** задаётся заново (не копируется). По умолчанию система предлагает **следующий числовой номер** (на основе `versionNumber` в цепочке); пользователь может **переопределить** строку **`version`** произвольным значением. Значение **`version`** должно быть **уникально в пределах родительского `Component`** (конфликт → `409 Conflict`). Исходящие `DEPENDS_ON` копируются **без фильтра по статусу цели**, вместе с контекстом (`consumer`, `provider`).
- Линейность `INHERITED` определяет порядок версий компонента; в составе релиза приложения (§5.1) допускается выбирать **любую последующую** `ComponentVersion` без требования поочерёдных релизов приложения для промежуточных версий.
- При **`draft → active`** (публикация при релизе приложения): учёт черновика переходит из `HAS_DRAFT` в опубликованные: создаётся ребро **`HAS_VERSION`** к новой версии; **прежние** рёбра **`HAS_VERSION`** к другим опубликованным версиям того же компонента **сохраняются** (каталог и impact должны видеть все опубликованные линии). `INHERITED` сохраняется. Глобальный статус прежних линий **пересчитывается** по правилу §3.0.1 после записи `HAS_COMPONENT` нового релиза.
- При публикации **`draft → active`** системой отображается **обязательное предупреждение**, если среди исходящих `DEPENDS_ON` черновика присутствуют цели в статусе **`deprecated`** или **`unactive`**; публикация **не блокируется**, ответственность за чистоту состава лежит на пользователе. Вычисляемое поле **`readyToProduction`** у **`FeatureVersion`** (§6) **зависит** от готовности **исходящих cross-unit** `DEPENDS_ON` состава черновика фичи; same-unit `DEPENDS_ON` и глобальный статус цели сами по себе критерий готовности фичи **не** задают.
- **Отражение прод-состояния** `ComponentVersion` (§3.0.1) в графе **выполняется при релизе и откате приложения** (§5.1, §5.2): записывается прикладной статус на `HAS_COMPONENT`, затем пересчитывается глобальный статус. **В UI** пользователь задаёт прикладной статус строки состава **только** в визарде релиза ([ui-spec §4](./frontend/ui-spec.md)). Отдельного API ручного перехода глобального статуса `ComponentVersion` **нет**.

### 4.1. Интеграции на `deprecated` и `unactive`

- **Новая фича** (первый `FeatureVersion` / создание фичи без наследуемой модели связей): создавать новые связи, ведущие на **`deprecated`** `ComponentVersion`, **запрещено**; пользователю показывается уведомление с причиной.
- **Новая версия существующей фичи**: можно **сохранить** связь на **`deprecated`**, если **та же логическая связь уже существовала** в предыдущей опубликованной версии функционала (наследование без расширения интеграций на deprecated).
- На **`unactive`** новые связи **не создаются** (ни для новой фичи, ни при копировании).

## 5. Версии приложения (`Application` / `ApplicationVersion`)

- Версионирование только через ноды **`ApplicationVersion`**; **`HAS_DRAFT` для приложения не используется**.
- Новое приложение после создания **может не иметь** ни одной **`ApplicationVersion`**, пока не выполнен первый релиз через API/UI (**§5.1**). Первая зафиксированная версия получает **`versionNumber = 1`**, статус **`current`**, без входящего ребра **`INHERITED`** (нет предшественника). Строка **`version`** для релиза по умолчанию — **`"1"`**; пользователь может задать **любую** уникальную в пределах **`Application`** строку (см. §8.1).
- Структура рёбер:
  - `(Application)-[:HAS_VERSION]->(ApplicationVersion)` — ко всем выпущенным версиям (`current`, `previous`).
  - `(ApplicationVersion)-[:INHERITED]->(ApplicationVersion)` — линейная история релизов.
  - `(ApplicationVersion)-[:HAS_COMPONENT {status}]->(ComponentVersion)` — состав релиза; **`status ∈ { active, deprecated }`**; допускается **несколько** `ComponentVersion` одного компонента (миграция), но **не более одной** строки со `status = active` на один `Component` внутри одной `ApplicationVersion`. Состав, где у компонента все строки `deprecated` (нет `active`), **допустим**.
- Инварианты:
  - Либо у приложения **нет** ни одной **`ApplicationVersion`**, либо ровно **одна** из них со статусом **`current`**; все остальные выпущенные версии — **`previous`** (история); количество `previous` **не ограничено**.
  - Приложение включает только `ComponentVersion` **своего** юнита (cross-unit через `HAS_COMPONENT` **запрещён**; межюнитные контракты — только `DEPENDS_ON`, §8).
- При **новом релизе** (если уже есть **`current`**): создаётся новая `ApplicationVersion` со статусом `current`; прежняя `current` переводится в `previous`; цепочка `INHERITED` обновляется так, чтобы история релизов оставалась линейной. При **первом релизе** прежней `current` нет: создаётся одна **`ApplicationVersion(current)`** с **`versionNumber` = 1** и задаются рёбра **`HAS_COMPONENT`** (см. §5.1).

### 5.1. Процесс pre-release (обобщённо)

1. Если у приложения **уже есть** выпущенные версии: от **`ApplicationVersion` со статусом `current`** формируется список строк состава из исходящих рёбер **`HAS_COMPONENT`** (включая прикладной `status`). Если это **первый релиз** приложения (рёбер **`HAS_VERSION`** от **`Application` ещё нет**): начальный список состава **пуст** — пользователь добавляет только те **`ComponentVersion`**, которые войдут в первый релиз (**минимум одна** строка состава; пустой релиз недопустим).
2. Пользователь формирует будущий состав: добавляет/убирает версии и задаёт **прикладной статус** каждой строки (`active` | `deprecated`) в UI визарда.
   
   **Ввод компонента в состав приложения:** если у `Component` **нет** ни одной `ComponentVersion` в `HAS_COMPONENT` у `ApplicationVersion` со статусом `current`, пользователь может включить в будущий релиз любую существующую `ComponentVersion` этого компонента в статусах **`active`**, **`deprecated`** или **`draft`**. Правило перескока по `INHERITED` (ниже) к такому случаю **не** применяется. Статус **`unactive`** при первом включении компонента в состав данного приложения **не** допускается. Прикладной статус новой строки по умолчанию равен глобальному статусу версии (`active` / `deprecated`); для `draft` — всегда `active` (публикация при Release).
   
   **Выбор версии компонента при релизе (перескок вперёд):** если компонент **уже** представлен в составе `current`, для каждого такого `Component` допустимо указать **любую** существующую `ComponentVersion`, которая находится **позже** текущей версии этого же компонента в этом составе по линейной цепочке **`INHERITED`** (§4). Не требуется выпускать промежуточные релизы приложения для последовательного перехода на каждую следующую `ComponentVersion`. В UI визарда релиза перескок вперёд делается так: **замена в строке** таблицы состава (`Select` по `newerVersions` из `release-components`, семантика «убрать + добавить») **или** добавление более новой CV второй строкой через модалку каталога. В обоих местах UI допускается **прокси** «позже»: `versionNumber` строго больше текущей / максимальной среди строк этого компонента в **будущем** составе; нормативное правило по цепочке **`INHERITED`** при этом сохраняется (уточнение фильтра по цепочке — при появлении данных в каталоге).
   
   **Замена линии:** при **замене в строке** (Select) прежняя CV **сразу выходит** из будущего состава. При **добавлении** новой версии компонента, уже присутствующего в составе (модалка), прежняя строка **остаётся** со статусом **`deprecated`** (миграция) **или** пользователь **убирает** её из состава. Ручного выбора глобального `unactive` **нет**: глобальный `unactive` появляется только после пересчёта §3.0.1, когда версия исчезла из `current` **всех** приложений.
   
   Если в `current` одновременно присутствует **несколько** `ComponentVersion` одного `Component` (миграция), правило перескока применяется для замены **каждой** такой строки состава релиза относительно выбранной в ней текущей версии.
3. Для строк релиза, где выбранная `ComponentVersion` в статусе **`draft`**, при **Release** выполняется публикация **`draft` → `active`** (§4): создаётся `HAS_VERSION`, прежние `HAS_VERSION` **не** удаляются. Прикладной статус такой строки на ребре — **`active`**. Для строк со статусами **`active`** или **`deprecated`** отдельная публикация ноды **не** требуется.
4. По **Release**: если уже есть **`current`**, создаётся новая `ApplicationVersion` со статусом `current`, прежняя `current` переводится в `previous`, добавляется ребро **`INHERITED`** от новой версии к прежней **`current`**; если это **первый релиз**, создаётся **`ApplicationVersion(current)`** с **`versionNumber` = 1** без ребра **`INHERITED`** к предшественнику. Строка **`version`** новой `ApplicationVersion` задаётся в теле **`POST /api/application-versions/release`** (опционально; по умолчанию — следующий числовой номер относительно `current`, см. §8.1). Задаются рёбра **`HAS_COMPONENT {status}`** для новой версии. Затем **пересчитывается** глобальный `ComponentVersion.status` для объединения старого и нового составов (§3.0.1); при изменении статуса эмитится событие для автоактивации фич (§6).

Уточнение для API **`POST /api/application-versions/release`**: для первого релиза приложения параметр **`sourceApplicationVersionId` не передаётся**; при уже существующих версиях он **обязателен** и должен указывать на **`ApplicationVersion` со статусом `current`**. Тело содержит массив **`components: [{ componentVersionId, status }]`** (`status ∈ { active, deprecated }`); поле **`statusTransitions`** **не используется**.

Перед релизом UI вызывает **`POST /api/application-versions/release-preview`** (режим `release`): блоки последствий «в этом приложении» / «глобально» и изменения глобальных статусов (§5.3).

Детали UI — [ui-spec §4](./frontend/ui-spec.md); нормативно важны **`HAS_COMPONENT {status}`**, статусы `ApplicationVersion` и пересчёт глобальных статусов компонентов.

### 5.2. Откат к предыдущему прод-релизу (Revert)

- Операция **Revert** создаёт **новую** `ApplicationVersion` со статусом **`current`**; прежняя **`current`** переводится в **`previous`**; добавляется ребро **`INHERITED`** от новой версии к прежней `current`, как при обычном релизе (линейная история).
- Состав **`HAS_COMPONENT`** новой версии — **копия** множества рёбер **`HAS_COMPONENT`** у **непосредственного предшественника** текущей версии по **`INHERITED`**, **включая свойства `status`**.
- После записи состава выполняется **пересчёт** глобальных `ComponentVersion.status` (§3.0.1): версии, ставшие `unactive` после предыдущего релиза, могут снова получить `active` или `deprecated` («оживление»). Откат **не блокируется** наличием глобально `unactive` в снимке.
- Если у текущей версии **нет** предшественника по **`INHERITED`** (в приложении только один выпущенный релиз), операция **недопустима**.
- В снимке предыдущего релиза **не** должно быть ссылок на **`ComponentVersion`** в статусе **`draft`**; иначе откат отклоняется (аномалия данных).
- Перед откатом UI вызывает **`release-preview`** (режим `revert`) и показывает модалку последствий (§5.3).
- Revert **не** является механизмом произвольных обратных переходов статусов: это создание **новой** `ApplicationVersion` с составом предыдущего релиза и пересчётом производных статусов.

### 5.3. Предпросмотр последствий (`release-preview`)

`POST /api/application-versions/release-preview` принимает режим `release` | `revert`, идентификатор приложения и (для релиза) будущий состав `components`. Ответ:

1. **`inThisApplication`** — для каждой версии, **уходящей** из состава данного приложения: фичи с ребром `USES_COMPONENT_VERSION` где `applicationId` = это приложение; рёбра `DEPENDS_ON`, у которых на стороне consumer или provider `application_id` = это приложение.
2. **`global`** — заполняется **только** для версий, которые после операции станут глобально `unactive` (исчезнут из `current` всех приложений): все потребители и связанные сервисы по всем приложениям (§3.1).
3. **`globalStatusChanges`** — версии, чей глобальный статус изменится (включая публикацию `draft → active` и «оживление» при откате).

Подтверждение последствий в UI (чекбокс) **обязательно**, если заполнен блок 1 или 2; операция при этом **не блокируется** API.

### 5.4. Переименование метки релиза (Rename)

- Операция **Rename** меняет **только** строку **`ApplicationVersion.version`** у версии со статусом **`current`**.
- **`versionNumber`**, рёбра **`HAS_COMPONENT`**, статус и цепочка **`INHERITED`** **не** изменяются.
- Значение нормализуется через **`trim`**; пустая строка после `trim` → **`400 Bad Request`**.
- Уникальность в пределах родительского **`Application`** — по правилам §8.1 (после `trim`, с учётом регистра); конфликт → **`409 Conflict`**.
- Смена только регистра у **той же** ноды (например `"1.0-rc"` → `"1.0-RC"`) **допустима**.
- Для статуса **`previous`** операция **недопустима** (`400`).
- API: **`PATCH /api/application-versions/:id`** с телом `{ "version": "<string>" }` (см. [api.md](./api.md)); UI — [ui-spec §3.4](./frontend/ui-spec.md).

## 6. Версии функционала, эпик и переход черновика в `active`

Статус версии фичи отражает готовность и жизненный цикл функционала; смена статуса не затрагивает статусы компонентов и релизы приложений (**подробнее в §3.0.2**).

Правила полей `readyToProduction` и `canAutoActive` у `FeatureVersion`.

- У **Feature** может быть только **один** черновик версии (`HAS_DRAFT`).
- При создании нового `Feature` автоматически создаётся первая `FeatureVersion` со статусом `draft` (без `INHERITED`).
- При создании новой **`draft`** существующей фичи строка **`version`** по умолчанию — **следующий числовой номер** по `versionNumber`; пользователь может **переопределить** её произвольной строкой. **`version`** должна быть **уникальна в пределах родительской `Feature`** (конфликт → `409 Conflict`, §8.1).
- **Черновик** (`FeatureVersion` в статусе `draft`) отражает **желаемые изменения**: набор и цели рёбер **`USES_COMPONENT_VERSION {id, applicationId}`** → **`ComponentVersion`**. Свойство **`applicationId`** обязательно: идентификатор родительского **`Application`**, в контексте которого фича использует версию. Если одна версия используется в двух приложениях, создаются **два** ребра. Прямых рёбер `Feature ↔ Application` **нет**.
- Версия **остаётся в `draft` до публикации**: постановка и состав ещё могут меняться (ошибки аналитики/постановки, неучтённые кейсы). Переход `draft → active` фиксирует снимок (`PINNED_TO_APPLICATION_VERSION`).
- Новая `draft` существующей фичи наследует связи `USES_COMPONENT_VERSION` от текущей `active` **вместе с `applicationId`**.
- При создании новой `draft` также **копируются** исходящие рёбра **`DEPENDS_ON`** состава предыдущей версии: берутся рёбра от CV с `USES` предыдущей FV, у которых в контексте `consumerFeatureVersionId` = id предыдущей FV; создаются **новые** рёбра между теми же CV с тем же прикладным контекстом (`applicationId` / `serviceId` и т.д.), но с `consumerFeatureVersionId` = id нового draft (при same-feature, когда `providerFeatureVersionId` совпадал с предыдущей FV, он тоже переписывается на новый draft). Исторические рёбра предыдущей FV **не** изменяются.
- В режиме редактирования `FeatureVersion(draft)` отображаются связи `DEPENDS_ON` только тех `ComponentVersion`, которые входят в состав черновика по `USES_COMPONENT_VERSION`, с фильтрацией по контексту текущей `FeatureVersion` (в т.ч. `applicationId`).
- При редактировании черновика можно удалить привязку (ребро `USES_COMPONENT_VERSION`) или переключить на другую версию / другое приложение. Приложение выбирается: из `current`-состава приложений, где уже есть версия; для версии вне приложений (design-time / `draft`) — из списка приложений юнита (планируемое приложение). Приложение должно принадлежать **тому же юниту**, что и `ComponentVersion`.
- **Запрет дубля привязки:** повторное добавление той же пары `(ComponentVersion, applicationId)` в одну `FeatureVersion` **запрещено** → **`400`**, сообщение «Такая версия компонента уже добавлена в это приложение»; при любом таком дубле в `add` отклоняется весь запрос, рёбра не создаются. Разные `ComponentVersion` (в т.ч. одного `Component`) и та же CV с **другим** `applicationId` — **допустимы**. API: `POST /api/feature-versions/bind-component-versions` ([api.md](./api.md), [diagrams-frontend.md](./diagrams-frontend.md)).
- При редактировании черновика можно **удалить** исходящее ребро **`DEPENDS_ON`**, у которого в контексте `consumerFeatureVersionId` = id этого draft (физический `DELETE` копии; ключ — пара CV и `consumerApplicationId` / `providerApplicationId` из контекста). Рёбра других `FeatureVersion` с тем же путём CV→CV **не** затрагиваются. API: `POST /api/edge/depends-on/delete` ([api.md](./api.md)); UI — [ui-spec §9](./frontend/ui-spec.md).
- **Поднять версию компонента в черновике (UI «Поднять версию»):** атомарная операция на `FeatureVersion(draft)` — заменить цель одного ребра `USES_COMPONENT_VERSION {applicationId}` на более новую `ComponentVersion` того же `Component` (при отсутствии подходящей — создать новую `draft` по правилам §4), выровнять исходящие `DEPENDS_ON` потребителя с тем же `consumerApplicationId` под набор исходной CV (`consumerFeatureVersionId` = этот draft) и перенести входящие `DEPENDS_ON` этого draft на старую CV с `providerApplicationId` = тот же `applicationId` на новую CV (чтобы прежняя версия не оставалась на диаграмме состава). Другие `applicationId` той же FV **не** затрагиваются. Операция **не** создаёт новую `FeatureVersion`, **не** пишет `HAS_COMPONENT` / релиз приложения и **не** создаёт `PINNED_TO_APPLICATION_VERSION` (эквивалент ручной цепочки create CV + bind + DEPENDS_ON; готовность и pin — по общим правилам ниже). API: `POST /api/feature-versions/raise-component-version` ([api.md](./api.md)).
- **`FeatureVersion` в статусе `active`** трактуется как **эпик** — обобщение доработки по компонентам; набор ссылок на **`ComponentVersion`** **не обязан** образовывать жёсткий «единый срез» с номером или статусом самой фичи.
- После фиксации намерения в черновике следует **реализация** и **релизы компонентов на прод** (в т.ч. через релиз **`ApplicationVersion`**, §5.1 и §4).
- **Критерий готовности черновика к переводу в `active`:** у черновика есть **хотя бы одно** исходящее ребро `USES_COMPONENT_VERSION`, и для **каждого** такого ребра `(FeatureVersion в draft)-[:USES_COMPONENT_VERSION {applicationId}]->(ComponentVersion)` существует путь `(Application {id: applicationId})-[:HAS_VERSION]->(ApplicationVersion {status: 'current'})-[:HAS_COMPONENT {status ∈ {active, deprecated}}]->(ComponentVersion)`. Дополнительно: для **каждого исходящего cross-unit** ребра `DEPENDS_ON` от `ComponentVersion` состава черновика (разные `unitId` у концов; направление consumer → provider) существует путь `(Application {id: provider.application_id})-[:HAS_VERSION]->(ApplicationVersion {status: 'current'})-[:HAS_COMPONENT {status ∈ {active, deprecated}}]->(provider ComponentVersion)`, где `provider.application_id` — из контекста ребра (§7.2). Глобальный статус `ComponentVersion` сам по себе **не** достаточен: важна пара «приложение, версия». При **отсутствии** исходящих `USES_COMPONENT_VERSION` критерий **не выполнен** (публиковать нечего). Пустой набор cross-unit рёбер готовность **не** блокирует.
- **`readyToProduction` (вычисляемый):** принимает значение `true`, когда выполнен критерий предыдущего пункта; при нуле привязок `USES` — всегда `false`.
- **Ручной пересчёт готовности:** доменная операция проверки готовности может вызываться вручную (`POST /api/feature-versions/check-ready`); её результат обязан соответствовать критерию готовности, определённому в этом разделе, и включать разбор по каждой привязке `USES_COMPONENT_VERSION` и по каждому исходящему cross-unit `DEPENDS_ON` (приложение, компонент, версия, статус в `current`-релизе, причина неготовности). При пустом составе ответ содержит reason уровня версии `no_component_bindings`. См. [api.md](./api.md).
- **Запрет публикации пустого черновика:** переход `FeatureVersion` `draft → active` (ручной и через автопереход) **запрещён**, если у черновика нет ни одного ребра `USES_COMPONENT_VERSION`; API отвечает **`400`** с сообщением «Нет связанных компонентов». Запрет касается **только** пустого состава; при наличии привязок правила публикации остаются прежними (в т.ч. блокировка при неготовых cross-unit связях).
- **Автоматический переход:** при `canAutoActive = true` черновик автоматически переводится в статус **`active`** и переносится учёт с **`HAS_DRAFT`** на **`HAS_VERSION`**, когда `readyToProduction = true` (в т.ч. после события смены статуса `ComponentVersion` при релизе/откате приложения).
- При `canAutoActive = false` черновик при `readyToProduction = true` не публикуется автоматически и переводится в `active` вручную.
- **Снимок релизов приложений при публикации:** при переходе `FeatureVersion` `draft → active` (ручной и через автопереход) система создаёт рёбра **`PINNED_TO_APPLICATION_VERSION`** от этой версии ко всем релевантным **`ApplicationVersion` со статусом `current` на момент активации**. Набор приложений — **distinct** идентификаторы из:
  - `USES_COMPONENT_VERSION.applicationId` состава черновика;
  - `providerApplicationId` (контекст исходящих `DEPENDS_ON` от CV состава с `consumerFeatureVersionId` = этой FV, §7.2).
  Для каждого такого `Application` резолвится ровно один `ApplicationVersion {status: 'current'}`, через который выполняется путь `HAS_COMPONENT` к соответствующему `ComponentVersion` (для USES — цель ребра; для provider — CV-поставщик). Если для любого приложения путь не найден — активация **запрещена** (`400`), статус черновика **не** меняется, рёбра `PINNED_*` **не** создаются. У **`draft`** рёбер `PINNED_TO_APPLICATION_VERSION` **нет**. После успешной записи рёбра **иммутабельны**: не обновляются при последующих релизах приложения, при `active → unactive` и при `unactive → active` (повторная активация **не** пересоздаёт снимок).
- **Задел на расхождения с `current`:** сравнение снимка (`PINNED_TO_APPLICATION_VERSION` + состав pinned AV) с актуальным `ApplicationVersion(current)` / составом (CV ушёл из релиза и т.п.) — **вне текущего scope**; свойств «расхождение» на ребре **не** вводится — будущий diff строится query-time по неизменяемому снимку.
- **Область проверки критерия:** исходящие **`USES_COMPONENT_VERSION`** от **черновика** данной фичи **и** исходящие **cross-unit** `DEPENDS_ON` от CV состава этого черновика. **Входящие** cross-unit рёбра и same-unit `DEPENDS_ON` **не** участвуют. У **текущей `active` `FeatureVersion`** той же фичи рёбра на версии, уже не входящие в `current` указанного приложения, **допустимы** как исторический след и **не участвуют** в проверке готовности черновика.
- **Предыдущая опубликованная линия:** при появлении новой **`active` `FeatureVersion`** прежняя **`active`** **переводится в `unactive`** (линейная история, согласованность с §3.0.2 и инвариантами §14).

## 7. Контракты между версиями компонентов (`DEPENDS_ON`)

- Единственный канонический способ выразить потребление контракта другой версии компонента — ребро **`DEPENDS_ON`** от **`ComponentVersion`** к **`ComponentVersion`**.
- Между одной парой `ComponentVersion` допускаются **две противоположные** направленные `DEPENDS_ON` (`A→B` и `B→A`): это **два** контракта (например отправка данных и приём результата), а не undirected-ребро.
- Узлы вида `FeatureConnection`, `FeatureConnectionVersion`, промежуточные «соединения» фич/сервисов **не** используются.
- На ребре **`DEPENDS_ON`** контекст взаимодействия хранится как **typed properties отношения** (camelCase ids: `consumerServiceId`, `consumerApplicationId`, `consumerFeatureId`, `consumerFeatureVersionId`, `providerServiceId`, `providerApplicationId`, `providerFeatureId`, `providerFeatureVersionId`), чтобы восстановить бизнес-смысл (в т.ч. cross-unit и межсервисные сценарии):
  - идентификаторы **`Service`** (сторона потребителя и сторона поставщика контракта, при необходимости — два разных юнита);
  - идентификаторы **`Application`** с каждой стороны (если применимо);
  - идентификаторы **`Feature`** и/или **`FeatureVersion`**, от которых смыслово исходит использование контракта с каждой стороны.
- Контекст `DEPENDS_ON` при создании связи задаётся вручную пользователем, **выводится системой** в сценарии same-feature (§7.2), или наследуется при копировании из предыдущей `active` версии компонента.
- Участвующие компоненты — любые `Component` с `type ∈ { component, dependency }`; публичность cross-unit — по §8 и флагу **`isPublic`** у **родительского `Component`** стороны поставщика (по целевой `ComponentVersion` в направлении зависимости).

### 7.2. Правило заполнения контекста `DEPENDS_ON`

- На каждой стороне связи (`consumer` и `provider`) **контекст заполняется полностью**: `service_id`, `application_id`, `feature_id`, `feature_version_id`. Пустая или частично заполненная сторона **не допускается** при создании или редактировании ребра.
- **`application_id`** — идентификатор родительского **`Application`** (не `ApplicationVersion`). Поле **обязательно** в том числе для черновых (`draft`) `ComponentVersion`.
- **Same-feature (из `FeatureVersion(draft)`):** если оба конца `DEPENDS_ON` входят в состав этой версии по `USES_COMPONENT_VERSION`, контекст **допускается выводить системой** без ручного ввода полей в UI: `feature_version_id` / `feature_id` — текущий draft и его родитель; `service_id` — активный `AGGREGATES` этой Feature (первый неснятый); `application_id` — из `USES_COMPONENT_VERSION.applicationId` соответствующей стороны. API: `POST /api/edge/depends-on/from-feature-versions` с одним и тем же `FeatureVersion` на обеих сторонах.
- **Cross-unit** (диалог «Связь с другим юнитом» с `FeatureVersion(draft)`): `application_id` потребителя берётся из `USES_COMPONENT_VERSION.applicationId` ноды, с которой открыт диалог; `application_id` поставщика — из каскада `Unit → Service → Feature → FeatureVersion → Application → ComponentVersion` по `USES` выбранной версии фичи (при одном приложении в составе — вывод системой; при нескольких — ручной выбор шага Application). Создание **`Application`** в этом сценарии **запрещено** (в т.ч. в чужом юните). Автоматический вывод из состава `ApplicationVersion` сам по себе обязательный ввод не заменяет.
- Обе стороны (`consumer` и `provider`) **обязательны** с полным набором четырёх полей (на ребре в данных, независимо от того, заполнены ли поля вручную в UI).

## 8. Изоляция по юнитам и публичность

- **Unit** — вершина изоляции: private-сущности **`Component`**, **`Service`**, **`Application`**, **`Feature`** (а также ноды версий **`Component`**, **`Feature`** и **`Application`**, не предназначенные для внешнего использования) имеют `unit_id` и связываются **внутри** юнита. **`Service` в нормативной модели не имеет нод версий** (§2.1).
- **Cross-unit** допускается **только** если у **компонента-поставщика** (родитель целевой **`ComponentVersion`** в направлении зависимости) **`Component.isPublic = true`**, и межюнитный контракт явно оформлен через **`DEPENDS_ON`** с корректным контекстом на ребре.
- Новые интеграции на **`deprecated`** — по правилам §4.1 (запрет для новой фичи; наследование для новой версии существующей).

### 8.0. Связность двух юнитов и отображение на диаграммах

- Отдельного ребра **`Unit → Unit`** в модели **нет**: «связаны два юнита» означает наличие пути по графу, в котором **ключевой межюнитный мост** — **`ComponentVersion -[:DEPENDS_ON]-> ComponentVersion`** (и контекст на ребре по §7) при соблюдении правил **cross-unit** выше.
- Обход от юнита к участвующим сущностям опирается на рёбра §1.1: например **`Unit -[:PROVIDES]-> Service -[:AGGREGATES]-> Feature`**, **`Unit -[:STAKEHOLDER]-> Feature`**, **`Unit -[:OWNS]-> Application`**, далее **`FeatureVersion -[:USES_COMPONENT_VERSION]-> ComponentVersion`**, **`ApplicationVersion -[:HAS_COMPONENT]-> ComponentVersion`**. Прямых рёбер **`Feature ↔ Application`** и **`Application ↔ Component`** в каноне **нет**; в продуктовой формулировке «unit → service → feature → application → component → … → другой unit» участки «feature–application–component» читаются **только через версии** и перечисленные типы рёбер.
- **Создание** межюнитной связи в данных — через появление/редактирование соответствующего **`DEPENDS_ON`** (и соблюдение **`Component.isPublic`** у поставщика, контекста, §4.1, §10), а не через отдельную сущность «связь юнитов».
- **На диаграммах в UI** допускается одновременно показывать **родительские сущности** (`Unit`, `Service`, `Feature`, `Application`, `Component`, …) и **ноды версий** (`FeatureVersion`, `ComponentVersion`, `ApplicationVersion`, …): зритель видит полный контекст, при этом **межюнитный контракт** в графе выражен **между версиями компонентов** (`DEPENDS_ON`), а не ребром между родителями.

### 8.1. Уникальность имён и нормализация

- Для сущностей с атрибутом **`name`** и изоляцией в юните (например `Team`, `Application`, `Service`, `Feature`, `Component`) имя должно быть уникально **в пределах одного юнита и типа сущности**.
- Для **`Unit`** имя должно быть уникально **глобально** (среди всех `Unit`) и не должно зависеть от `unit_id` (так как `Unit` — вершина изоляции).
- При **создании** значения `name` применяется нормализация: **`trim`** (удаление ведущих и конечных пробелов).
- Проверка уникальности `name` выполняется **без учёта регистра**.

Ноды версий (`ComponentVersion`, `FeatureVersion`, `ApplicationVersion`) не имеют отдельного «имени версии»; идентификация версии в пользовательском смысле задаётся связкой **родительская сущность + `version`**.

- Атрибут **`version`** (строка) **уникален в пределах родителя** (`Component`, `Feature` или `Application`): две версии одного родителя не могут иметь одинаковое значение **`version`** (после `trim`); нарушение → **`409 Conflict`**.
- **`versionNumber`** (целое) остаётся **техническим порядковым номером** в линейной цепочке `INHERITED` / истории релизов; система **предлагает** следующий номер как значение **`version` по умолчанию**, но пользователь может задать **произвольную строку** (гибридная модель: semver, hotfix-метки и т.д.).

## 10. Production vs design-time

- **Production graph** (для отображения «как на проде» и режима **`on-prod`** impact):
  - для **`ComponentVersion`**: прод-семантика статусов определяется в [§3.0.1](#301-componentversion-прод-семантика-и-статусы); в production-проекции рёбра **`DEPENDS_ON`** и иные, указывающие на **`unactive`** там, где для режима «текущий прод» это неконсистентно, — **аномалии** и подсвечиваются (см. §10).
  - для **`FeatureVersion`**: **`draft`** относится к **design-time**; опубликованная линия в фокусе прод-проекции — статусы **`active`** и **`deprecated`** по смыслу §3.0.2. Рёбра **`USES_COMPONENT_VERSION`** от **`active` `FeatureVersion`** к **`unactive` `ComponentVersion`** **не** считаются нарушением **критерия готовности черновика** (§6) и в прод-проекции трактуются как **допустимый исторический след**, а не как сигнал блокировки автоперехода черновика. Тот же след (и `USES` от **`draft`**) может участвовать в **UI-предупреждениях** по клику на треугольник ([ui-spec.md §8.5](./frontend/ui-spec.md)) — это **не** отождествляется с критерием §6.
  - для **`ApplicationVersion`**: в фокусе прод-проекции версия со статусом **`current`**; история релизов — **`previous`**.
  - для **состава услуги** (`Service -[:AGGREGATES]-> Feature`): в фокусе прод-проекции учитываются рёбра **без** `deleted: true`; рёбра с **`deleted: true`** — история (детали §2.1).
- **Design-time**: включает **`draft`** для планирования черновиков **`Component`** и **`Feature`** (не для версий приложения).
- Режим отображения по умолчанию для операционных сценариев (в т.ч. «какие другие юниты связаны с текущим») — **`on-prod`** (production-проекция).
- Режим **`draft`** используется на этапе design при создании и анализе черновиков (design-time / история, в т.ч. снятые `AGGREGATES`).

## 13. Impact analysis

Два режима:

1. **режим `draft`** — все рёбра и версии, включая версии со статусом **`draft`**, и предупреждения.
2. **режим `on-prod`** — только production-проекция (см. §10); аномалии перечисляются отдельно.

Влияние должно раскрываться до: компонентов, приложений, фич, сервисов, команд, юнитов.
Точка запуска impact analysis — произвольная нода графа: сущности-родители (`Unit`, `Team`, `Service`, `Feature`, `Application`, `Component`) и ноды версий (`ComponentVersion`, `FeatureVersion`, `ApplicationVersion` и др.); сценарий §13.1 — частный нормативный случай для старта от команды.

### 13.1. «Область влияния команды» (нормативное определение)

Под «областью влияния команды» (для UI/отчётов) понимается набор сущностей, достижимых от команды как владельца компонентов, с раскрытием как «внутриюнитного», так и cross-unit контуров.

**Стартовая точка:** `Team` в текущем контексте.

**Компоненты команды:**

- базовый набор — все `Component`, для которых существует ребро `Team -[:MAINTAINS]-> Component`;
- версии для анализа зависят от режима:
  - в **режиме `on-prod`**: только production-проекция по правилам §10 и [§3.0.1](#301-componentversion-прод-семантика-и-статусы);
  - в **режиме `draft`**: включая версии со статусом **`draft`** и **`unactive`** (с пометками/предупреждениями по §10–§13).

**Приложения, в которые встроены компоненты команды:** любые `Application`, у которых существует путь

- `Application -[:HAS_VERSION]-> ApplicationVersion -[:HAS_COMPONENT]-> ComponentVersion -(родитель)-> Component`,

где `Component` принадлежит набору «компоненты команды», а `ApplicationVersion` выбирается согласно режиму (§10).

**Фичи, состоящие из компонентов команды:** любые `Feature`/`FeatureVersion`, у которых существует путь

- `Feature -[:HAS_DRAFT|HAS_VERSION]-> FeatureVersion -[:USES_COMPONENT_VERSION]-> ComponentVersion -(родитель)-> Component`,

где `Component` принадлежит набору «компоненты команды», а `FeatureVersion` и `ComponentVersion` фильтруются по режиму (§10).

**Сервисы, в которые входят такие фичи:** любые `Service`, для которых существует путь

- `Service -[:AGGREGATES]-> Feature`,

где `Feature` входит в набор «фичи, состоящие из компонентов команды». В **режиме `on-prod`** учитываются только активные рёбра `AGGREGATES` (без `deleted: true`, §2.1).

**Компоненты, взаимодействующие с компонентами команды:** любые `ComponentVersion`/`Component`, связанные контрактами через `DEPENDS_ON` с версиями компонентов команды:

- соседние `ComponentVersion` по рёбрам `ComponentVersion -[:DEPENDS_ON]-> ComponentVersion` и/или входящим `DEPENDS_ON` (направление зависит от того, показываем ли мы «потребителей» и/или «поставщиков» контракта).

**Cross-unit расширение области влияния:** если на контуре взаимодействий присутствуют `DEPENDS_ON`, ведущие в другой юнит, то в область влияния включаются **юниты и сущности других юнитов**, которые достижимы от «компонентов, взаимодействующих с компонентами команды» с подъёмом к родителям (`Component`, далее при необходимости `Feature`/`Application`/`Service`) при соблюдении правил §8:

- cross-unit допустим только при `Component.isPublic = true` у **компонента-поставщика** и корректном контексте на ребре `DEPENDS_ON` (§7, §8);
- отдельного ребра `Unit → Unit` нет; связность между юнитами выражается путями через `DEPENDS_ON` между `ComponentVersion` (§8.0, §14).

Сценарий **«какие юниты связаны с текущим»** трактуется как обход графа от **`Unit`** (текущий контекст) по организационным и версионным рёбрам §1.1 с выходом на **`DEPENDS_ON`** между **`ComponentVersion`** разных юнитов и обратным подъёмом к чужому **`Unit`** (симметрично по цепочке приложений/фич/сервисов); отдельного ребра **`Unit → Unit`** нет (§8.0).

Следует **различать сценарии**: (1) **готовность эпика** — критерий по рёбрам **`USES_COMPONENT_VERSION`** только от **`draft` `FeatureVersion`** (§6); (2) **наследие опубликованной фичи** — **`active` `FeatureVersion`** с целями **`ComponentVersion` в `unactive`** или иными устаревшими связями для анализа влияния и предупреждений, без отождествления с критерием п. (1).
По умолчанию для продуктового отображения и анализа влияния применяется **режим `on-prod`**; **режим `draft`** предназначен для design-time работы с черновиками.

**Сервис и состав услуги:** по умолчанию «сервис затронут» / текущий состав услуги трактуются по **активным** рёбрам **`AGGREGATES`** (§2.1); рёбра с **`deleted: true`** — для полноты картины в **режиме `draft`** или отдельным уточнением продукта.

## 14. Инварианты модели

- Линейные цепочки `INHERITED` для версий одной сущности; **без ветвления**.
- Одна **`draft`** (где применимо: **`Component`**, **`Feature`**) на родителя; у **`Feature`** — одна **`active`** среди опубликованных; у **`Component`** глобально допускается **несколько** `active` (§3.0.1, §4); у **`Application`** версий в `draft` **нет** (§5).
- В составе одной `ApplicationVersion` у одного `Component` — **не более одной** строки `HAS_COMPONENT` со `status = active` (§5.1).
- Каждое ребро `USES_COMPONENT_VERSION` имеет **`id`** и **`applicationId`** (§6).
- Нет висячих ссылок при удалении; физическое удаление только **`draft`** без зависимых связей.
- **Audit / change log** хранится отдельно (sidecar), фиксирует переходы статусов и публикации.
- Production-проекция графа может временно содержать предупреждения; они **явно подсвечиваются**.
- Инварианты и жизненный цикл **`AGGREGATES`** (состав услуги) — §2.1.
