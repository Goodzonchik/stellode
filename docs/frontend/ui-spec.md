# Спецификация UI/UX

Описание пользовательского интерфейса, экранов, сценариев взаимодействия и рекомендаций по визуальному поведению. Этот документ является единственным источником, который отвечает за описание UI-поведения функционала приложения.

- Интерфейс строится на **[Ant Design](https://ant.design/components/overview/).

## 2. Глобальный контекст юнита

- **Глобальный контекст** (`UnitContext`) задаётся на `/units` действием **«Сделать основным»**. В шапке рядом с пунктом меню **«Юниты»** показывается `Tag` с именем выбранного юнита; если юнит не выбран — tag не отображается. Списковые страницы CRUD и часть диаграмм фильтруют данные по этому юниту.
- Маршруты с `:id` в URL (диаграмма юнита, `/units/:id/diagram/cross-unit`, детальные страницы) могут опираться на **id из пути**, а не только на выбор в шапке — см. [frontend-routes.md](./frontend-routes.md).

## 3. Списковые страницы (CRUD)

### 3.1. Общая структура

Каждая списковая страница (`/units`, `/applications`, `/services`, `/features`, `/teams`, `/components`) содержит:
- Таблицу сущностей, отфильтрованных по глобальному юниту (см. [frontend-routes.md](./frontend-routes.md)).
- Кнопку **«Создать»** → модальное окно (`Modal`).
- Ошибки загрузки, операций и случаи «нет данных» на списке — только через toast; баннер над таблицей не используется (**см. §8.1**).

Для **`/units`**: в строке таблицы дополнительно — переход на **диаграмму юнита** (`/units/:id/diagram`, §5.3).

- Для **`/applications`**: колонка **«Версия»** — строка `ApplicationVersion.version` со статусом **`current`**; если у приложения нет версий — **`-`**. Если `current` нет, но есть история (`previous`) — показать `version` с максимальным `versionNumber` и UI-меткой **«Неактивна»** (аномалия инварианта [spec.md §5](../spec.md); в данных статус остаётся `previous`). Рядом с **названием** приложения — **один** жёлтый треугольник (**см. §7.4**), если `hasStatusWarning = true`: в `ApplicationVersion(current)` есть `HAS_COMPONENT.status = deprecated` **или** на приложение ссылаются `USES` (FeatureVersion `draft` | `active` | `deprecated`) к `ComponentVersion(unactive)` с `applicationId` этого приложения; иначе маркера нет; tooltip: **«Есть компоненты с предупреждением (deprecated / unactive)»**. Клик по треугольнику открывает модалку (§8.5). В строке таблицы — кнопка **«Новый релиз»** → визард релиза (§4, `/applications/:id/release`); кнопка **«Состав»** → `/applications/:id/versions/current/diagram` (§5.3.2; нет `current` → 404).
- Для **`/services`**: в строке таблицы — бейдж **«Архив»** для `status = archive`; кнопки изменения состава и описания скрыты. **«Заархивировать»** / **«Вернуть из архива»** — модалки подтверждения (`POST /api/services/:id/archive` и `/unarchive`, [aggregates-api.md](../aggregates-api.md)). На **диаграмме услуги** пункт **«Снять фичу»** для архивного сервиса **не** показывается (состав read-only).
- Для **`/components`**:
  - Под шапкой страницы (заголовок + **«Создать»**), над таблицей — **один ряд** клиентских фильтров (AND), без повторного запроса к API:
    - **имя** — `Input`, substring после `trim`, без учёта регистра;
    - **команда** — `Select`, `allowClear`, плейсхолдер **«Все команды»** (команды текущего юнита); строки без команды (`—`) видны **только** при сброшенном фильтре;
    - **тип** — `Select`, `allowClear`, плейсхолдер **«Все типы»**, значения как в колонке: **«своя разработка»** / **«внешняя зависимость»**.
  - Сортировка кликом по заголовкам колонок **Название**, **Команда**, **Тип** (по умолчанию без сортировки; цикл asc → desc → сброс). Ключи: `name`; отображаемое имя команды (`—`, если нет); подпись типа. Колонки **Описание** и **Действия** без sorter.
  - Пустой результат фильтров — стандартное empty-состояние Ant Design Table (**без** toast; см. §8.1). Deep-link `?highlight=` при id в загруженных данных, но скрытом фильтрами: без подсветки и без toast mismatch (см. §7.3).

### 3.2. Создание сущности

- Модальное окно с полями сущности (`name`, `description`, специфичные поля).
- При сохранении бэкенд автоматически создаёт первую версию `draft` для **Component** и **Feature** ([spec.md §4](../spec.md), [spec.md §6](../spec.md)). Пользователь не проходит отдельный шаг создания версии. Для **`Component`** поле **`isPublic`** задаётся **только в этой модалке создания**, не продлевается отдельными полями версии ([spec.md §2, §3.3](../spec.md)). Тип **«разрабатываемый компонент / внешняя зависимость»** (канонически `type`, в UI/DTO может выражаться флагом `isDependency`) также задаётся **только при создании**.
- Для **`Application`** вершина **`ApplicationVersion` при создании приложения не создаётся** — первый прод-релиз выполняется только через визард «Новый релиз» ([§4](#4-визард-релиза-applicationversion), [spec.md §5](../spec.md)).
- Валидация `name`: trim, уникальность без учёта регистра в пределах юнита и типа сущности ([spec.md §8.1](../spec.md)).
- `name` задаётся при создании и далее **не редактируется**.

### 3.3. Редактирование сущности

- Редактирование через модальное окно или inline.
- Поля кроме `name` допускают редактирование ([spec.md §3.3.1](../spec.md)). Для **`Component`** поля **`isPublic`** и тип **«разрабатываемый компонент / внешняя зависимость»** после создания **не** редактируются (можно только менять описание и прочие поля, допустимые в канонике — [spec.md §3.3.1](../spec.md)).

### 3.4. Страницы версий

Страницы `/features/:id`, `/applications/:id`, `/components/:id` отображают список версий родительской сущности:
- Статус каждой версии (бейдж с цветовой кодировкой; для `deprecated` — жёлтый chip и жёлтый треугольник, **см. §7.4**).
- Для **`FeatureVersion(draft)`**: индикатор **`readyToProduction`** — бейдж, показывающий готовность черновика к переводу в `active` (§7.1).
- Для **`/features/:id`**: действия — переход на диаграмму версии, смена статуса `FeatureVersion`, удаление черновика (§3.5). Создание новой версии — модалка с полем **«Версия»** (предложенный следующий номер, редактируемый). В таблице **нет** колонки со списком версий компонентов. Колонки **«Количество компонентов»** и **«Количество команд»**: первое — число различных `ComponentVersion`, на которые есть исходящие `USES_COMPONENT_VERSION` у этой `FeatureVersion` (см. [spec.md §6](../spec.md)); второе — число различных `Team` с ребром `MAINTAINS` на родительский `Component` этих версий (см. [spec.md §1.1](../spec.md)), без исключений для `type = dependency` и команд другого юнита. При нуле в ячейке — **`—`**.
- Для **`/applications/:id`**: в **шапке страницы** (рядом с заголовком) — основная кнопка **«Новый релиз»** (primary) → переход в визард (§4); в таблице — кнопка **«Состав»** → `/applications/:id/versions/current/diagram` для строки `current`, иначе `/applications/:id/versions/{version}/diagram` (§5.3.2); для строки **`ApplicationVersion` со статусом `current`**, если в списке **больше одной** версии приложения, — кнопка **«Откат к предыдущему релизу»** (Revert, [spec.md §5.2](../spec.md)): подтверждение, затем создание новой текущей версии со снимком состава предыдущего релиза. При **единственной** `ApplicationVersion` кнопка отката **не** показывается (нет предыдущего релиза по `INHERITED`). Пока **нет ни одной** версии приложения, доступна только **«Новый релиз»** в шапке и переход к составу из строк недоступен (таблица пуста). В **ячейке «Версия»** у строки со статусом **`current`** — кнопка-иконка карандаша (tooltip **«Переименовать версию»**) → модалка **«Переименовать версию»** с полем **«Версия»** (предзаполнено текущим `version`); пустое значение после `trim` блокируется валидацией формы; ошибки submit — в теле модалки (§8.4); успех — `PATCH /api/application-versions/:id` ([spec.md §5.4](../spec.md)), обновление списка. У строк **`previous`** кнопки переименования **нет**.
- Для **`/components/:id`**: **смена статуса `ComponentVersion` на этой странице не выполняется**; целевые статусы и публикация `draft → active` задаются **только** в визарде релиза приложения (§4, [spec.md §5.1](../spec.md)). На странице — создание новой `draft` (модалка с полем **«Версия»**, предзаполненным предложенным следующим номером; значение можно изменить) и просмотр списка со статусами; **колонки действий в таблице нет** (удаление черновика с этой страницы не выполняется).

### 3.5. Удаление версий

- Доступно на странице версий **функционала** (кнопка в строке, где предусмотрено), **и** на диаграмме (контекстное меню ноды), **где реализовано**. Для **`ApplicationVersion`** физическое удаление из списка **`/applications/:id`** **не** предусмотрено (история релизов сохраняется; см. Revert §5.2 в [spec.md](../spec.md)). Для списка **`/components/:id`** удаление из строки таблицы **не** предусмотрено.
- Физическое удаление допускается только для **`draft`** без зависимых связей ([spec.md §3.2](../spec.md)).
- Перед удалением — модалка подтверждения.
- Если есть блокирующие связи: в модалке отображается перечень (тип связи, направление, целевая нода), кнопка «Удалить» **неактивна**.

## 4. Визард релиза ApplicationVersion

Отдельная страница-визард (`/applications/:id/release`), реализующая процесс pre-release → release ([spec.md §5.1](../spec.md)). Демо-граф с несколькими релизами приложений — seed в [`scripts/cypher/seed.cypher`](../../scripts/cypher/seed.cypher) (`npm run db:reset`, см. [AGENTS.md](../../AGENTS.md)).

**Единственная точка в UI** для операций релиза над **`ComponentVersion`**: публикация **`draft → active`** и задание **прикладного** статуса строки состава (`HAS_COMPONENT.status` = `active` | `deprecated`) — визард на шаге 1 ([spec.md §5.1](../spec.md)); другие экраны эти переходы не инициируют. Глобальный статус версии **производный** ([spec.md §3.0.1](../spec.md)).

**Состав версии приложения** (`/applications/:id/versions/:version/diagram`) — **только просмотр** состава `HAS_COMPONENT` в таблице (§5.3.2); добавление или удаление компонентов из релиза выполняется **исключительно** в визарде «Новый релиз» (§4). Создание **`DEPENDS_ON`** с этого экрана **не** выполняется (§9).

### 4.1. Вход в визард

- Кнопка **«Новый релиз»** в шапке страницы `/applications/:id` (ApplicationVersions).
- Кнопка **«Новый релиз»** в строке таблицы списка `/applications` → тот же визард (`/applications/:id/release`).
- Заголовок страницы визарда: **`Новый релиз: {name}`**, где `{name}` — имя приложения; пока имя не загружено или не найдено — **`Новый релиз`**.
- Если у приложения **уже есть** хотя бы одна **`ApplicationVersion`**, точка отсчёта состава — **только** версия со статусом **`current`** (не `previous`).
- Если релиз **не первый**, а версии со статусом **`current` нет** — toast `error`, форма визарда не открывается; page-level баннер не показывается (**см. §8.1**).
- **Первый релиз** (у приложения **ещё нет** ни одной `ApplicationVersion`): визард открывается с **пустым** составом на шаге 1; пользователь добавляет `ComponentVersion` через **модалку каталога** юнита (автозагрузка при открытии). В теле **`POST /api/application-versions/release`** поле **`sourceApplicationVersionId` не передаётся**; массив **`components`** содержит выбранные строки с прикладным `status`.

### 4.2. Шаги

**Шаг 1. Состав релиза**
- Если это **не первый** релиз: отображается список строк из **`current`** (рёбра `HAS_COMPONENT` с прикладным `status`). Если это **первый** релиз: стартовый список **пуст**.
- Фильтры таблицы состава: **имя** (`Input`) и **команда** (`Select`, `allowClear`, «Все команды») — независимы от фильтров модалки каталога.
- Колонка **«Версия»** — для строк с более новыми допустимыми CV: `Select` (текущая + кандидаты из `newerVersions` ответа `release-components`). Выбор новой версии **заменяет** CV в этой строке (семантика «убрать старую + добавить новую»: прикладной статус по умолчанию как при add; при `active` — demote остальных строк того же компонента). Откат к меньшей версии в Select **не** доступен. Если более новых нет — версия текстом.
- Колонка **«Статус в приложении»** — `Select` (`active` | `deprecated`) для каждой строки. Для `draft` статус зафиксирован как `active` (публикация при Release).
- У **названия компонента** в строке с прикладным `status = deprecated` — жёлтый треугольник (**см. §7.4**); tooltip: **«Устаревшая версия (deprecated)»**.
- Колонка **«Другие приложения»** — сколько других приложений держат эту версию в `current` и с какими статусами.
- Кнопка **«Убрать»** — исключить строку из будущего состава.
- При добавлении версии компонента, уже присутствующего в составе (модалка, вторая линия): если прикладной статус новой строки — `active`, прежние строки того же компонента автоматически получают `deprecated`; пользователь может убрать прежнюю или сменить статусы (не более одной `active` на компонент). Дефолт прикладного статуса новой строки — по [spec.md §5.1](../spec.md) (для `draft` — всегда `active`; иначе равен глобальному `active` / `deprecated`). Состав без `active`-строки у компонента допустим, показывается предупреждение.
- **Две версии одного компонента (миграция):** оставить текущую строку со статусом `deprecated` и **добавить** более новую через модалку (не через Select замены).
- **Каталог добавления (модалка):**
  - Кнопка **«Добавить компоненты»** открывает модалку; при открытии — автозагрузка каталога юнита (`POST /api/component-versions/for-unit`). Назначение: **новый** компонент в составе и/или **вторая** (более новая) линия при миграции. Замена версии в существующей строке — через Select в таблице, не через модалку.
  - Фильтры модалки: имя + команда (`Select`, `allowClear`) — независимы от фильтров таблицы состава.
  - Строка = компонент; версия — `Select` (рядом — глобальный статус и число приложений в `current`); по умолчанию выбирается версия с максимальным `versionNumber` среди допустимых.
  - Допустимые версии: без `unactive`; если компонент **уже** есть в будущем составе — только CV с `versionNumber` строго больше максимального среди строк этого компонента в составе (UI-прокси «позже по `INHERITED`», см. [spec.md §5.1](../spec.md)); иначе — `active` | `deprecated` | `draft`. Компонент без допустимых версий **не показывается**.
  - Мультивыбор (чекбоксы) + **«Добавить выбранные»**; после успешного добавления модалка **закрывается**.
- **Новый компонент** / **перескок вперёд** — по [spec.md §5.1](../spec.md).

**Шаг 2. Последствия**
- Только чтение: данные **`POST /api/application-versions/release-preview`** (режим `release`) — блоки «в этом приложении», «глобально» (версии, ставшие `unactive`), изменения глобальных статусов, публикация `draft` ([spec.md §5.3](../spec.md)).
- Если заполнен блок «в этом приложении» или «глобально», для перехода далее обязателен чекбокс **«Я понимаю последствия»**. Релиз API **не блокируется**.

**Шаг 3. Подтверждение и Release**
- Поле **«Версия релиза приложения»** — строка новой `ApplicationVersion` (предзаполнена следующим номером; [spec.md §8.1](../spec.md)).
- Сводка: исключены / новые / смена версии / без смены / публикация draft / прикладные статусы строк.
- Кнопка **«Выпустить»**: `POST /api/application-versions/release` с **`components: [{ componentVersionId, status }]`**.
- Недопустимый состав отклоняется **API** (тост/текст в форме).

### 4.3. Откат (Revert)

- На странице `/applications/:id` кнопка **«Откат»** у версии `current` (если есть предшественник по `INHERITED`) открывает модалку последствий: **`release-preview`** в режиме `revert`, те же блоки и чекбокс подтверждения.
- После подтверждения — `POST /api/application-versions/revert`. Откат копирует состав и статусы рёбер предшественника и пересчитывает глобальные статусы (в т.ч. «оживление» `unactive`).

## 5. Диаграммы

Диаграммы строятся через `@xyflow/react` с асинхронной ELK-раскладкой (`elkjs`, layered). На диаграммах отображаются **и родительские сущности, и ноды версий** ([spec.md §8.0](../spec.md), [diagrams.md](../diagrams.md)).

Ошибки загрузки, операций и случаи «нет данных» для диаграммы — только через toast; баннер над холстом не используется (**см. §8.1**).

**Контейнеры приложений (subflow).** На диаграммах team / service / feature-version / component и в деталях cross-unit bridge компоненты рисуются **внутри** рамки `Application`, если они входят в состав (`HAS_COMPONENT`) **и/или** (на feature-version / component) указаны в `USES_COMPONENT_VERSION.applicationId`. Каждая `ComponentVersion` проецируется в ноду **`Component` «Имя · версия»** (id ноды = id CV); два CV одного Component в одном приложении → **две ноды**. В нескольких приложениях → **копии** с меткой **`duplicate`** в рамке. `ApplicationVersion` схлопывается в контейнер («Имя · версия» в заголовке рамки). Жёлтый треугольник (**см. §7.4**) — в **правом верхнем** углу ноды CV, только если контейнер соответствует `ApplicationVersion(current)` **и** у копии есть `HAS_COMPONENT.status = deprecated`; рамку контейнера не маркируют; без ребра `HAS_COMPONENT` (membership только через `USES.applicationId`) — маркера нет. Рёбра `HAS_COMPONENT` внутрь контейнера не рисуются; `USES_COMPONENT_VERSION` ведёт в копию приложения из `applicationId`. Контейнер статичный. **Исключение — диаграмма юнита** ([§5.3](#53-диаграмма-юнита-diagramsunitid)): в контейнере — **обзорный** `Component` (id = родительский Component, без «Имя · версия»); жёлтый треугольник на обзорных нодах **не** показывается. Обзор cross-unit ([§5.5](#55-обзорная-cross-unit-диаграмма-diagramscross-unit)) контейнеров **не** использует. На **drill-down bridge** поверх Application есть ещё контейнер **`Unit`** (**подробнее в §5.5**).

### 5.0. Общие принципы отображения версий

В UI используются два режима визуализации (это проекция данных, а не изменение нормативной модели):

- **Обзорные диаграммы** (**team**/service/component): на холсте — `Service` / `Feature` / контейнеры `Application` с проекцией CV→`Component` «Имя · версия»; отдельные ноды `ApplicationVersion` / `FeatureVersion` / сырые `ComponentVersion` **не** рисуются (AV схлопнута в контейнер). **Диаграмма команды** — без ноды `Team` на холсте (**подробнее в §5.3.1**). Между CV состава видны **внутренние** рёбра `DEPENDS_ON` (оба конца в составе видимых приложений); внешний контекст соседей по `DEPENDS_ON` **не** подтягивается. Самостоятельной обзорной диаграммы приложения **нет**: `/applications/:id/diagram` → редирект на состав `…/versions/current/diagram` ([§5.3.2](#532-состав-версии-приложения-diagramsapplicationidversionversion)). **Диаграмма юнита** — отдельный обзорный режим ([§5.3](#53-диаграмма-юнита-diagramsunitid)): без ноды `Unit` и без `DEPENDS_ON` на холсте; обзорный `Component`; виртуальные `USES`. Обзор **cross-unit** — исключение: только юниты и мосты ([§5.5](#55-обзорная-cross-unit-диаграмма-diagramscross-unit)).
  - для `Feature` (где применяется слияние) — актуальная `FeatureVersion.status = active`;
  - для `Application` — текущая `ApplicationVersion.status = current`, **если** у приложения уже есть хотя бы одна выпущенная версия; иначе в обзорной ноде **нет** привязанного прод-релиза (до первого релиза через визард, [§4](#4-визард-релиза-applicationversion)).
- **Диаграммы версионированных сущностей**: если маршрут/контекст относится к конкретной версии (например `FeatureVersion(draft)`), то на холсте отображаются связи выбранной версии; для **feature-version** CV проецируются в `Component` «Имя · версия» внутри Application, а ноды Feature / FeatureVersion / Service **не рисуются** (контекст — в заголовке, [§5.4](#54-диаграмма-версии-фичи-diagramsfeature-versionid)). Маршрут **application-version** — таблица состава, не холст ([§5.3.2](#532-состав-версии-приложения-diagramsapplicationidversionversion)).

### 5.1. Универсальная диаграмма (`/{collection}/:id/diagram`)

- Граф сущности с нодами и рёбрами по модели ([spec.md §1.1](../spec.md)).
- Режим **`on-prod`** / **`draft`** (проекция графа) — автоматически по статусу сущности на маршруте (см. [frontend-routes.md](./frontend-routes.md)).
- Поддержка **impact analysis** через подсветку (§5.2).

### 5.2. Impact analysis (подсветка на диаграмме)

- Активируется действием в **контекстном меню ноды**: правый клик по ноде → **«Показать влияние»** (на **всех** универсальных диаграммах **кроме** обзорной диаграммы юнита, §5.3).
- Затронутые ноды **подсвечиваются** прямо на текущем графе (цветом, обводкой или opacity для незатронутых).
- Раскрытие влияния до: компонентов, приложений, фич, сервисов, команд, юнитов ([spec.md §13](../spec.md)).
- Режим impact соответствует режиму проекции диаграммы: **`on-prod`** для опубликованной линии (`active` / `current`), **`draft`** — при работе с версией со статусом **`draft`** ([frontend-routes.md](./frontend-routes.md)).
- Отдельной страницы нет — impact встроен в существующую диаграмму.

### 5.2.1. «Открыть в списке»

- ПКМ по ноде → пункт **«Открыть в списке»** (один текст для всех типов; в меню **перед** impact и прочими действиями ноды).
- Холсты: unit, team, service, service-integrations, feature-version, cross-unit (обзор и drill-down) — везде, где на холсте есть нода подходящего типа. Экран состава приложения (§5.3.2) — не холст, пункта нет.
- Тип ноды → список верхнего меню:

| Нода | Маршрут | `highlight` |
|------|---------|-------------|
| `Unit` | `/units` | id юнита (`node.id`) |
| `Team` | `/teams` | id команды |
| `Service` | `/services` | id услуги |
| `Feature` | `/features` | id функционала |
| `Application` | `/applications` | id приложения |
| `Component` / `dependency` | `/components` | id компонента |
| Проекция CV («Имя · версия», id на холсте = CV) | `/components` | **`componentId`** родителя (не id версии) |

- URL: `/{list}?highlight=<entityId>&ctx.unitId=<unitId>`; подсветка / `scrollIntoView` / toast — **подробнее в §7.3**.
- Показ пункта: только если `unitId` сущности **равен** юниту в шапке (UnitContext). Для `Unit` сравнивается `node.id` с юнитом шапки. Нет `unitId` у сущности (кроме `Unit`) → пункта нет. Чужой юнит → пункта нет.
- На feature-version при включённом **«Сравнить с предыдущей»** пункт **скрыт** (как impact, §5.4).

### 5.3. Диаграмма юнита (`/units/:id/diagram`)

- Обзорный **hub без ноды `Unit` на холсте**: команды (`Team`) и услуги (`Service`) из ответа API (рёбра `HAS_TEAM` / `PROVIDES` от Unit на холсте **не** рисуются); функционалы — через активные `AGGREGATES` (`Service → Feature`). Нода `Unit` в ответе API есть (имя для заголовка), на холсте **не** показывается. Ребро `STAKEHOLDER` **не** показывается. Видимое ребро **`OWNS`** на холсте **не** рисуется. `Application` — **контейнер** (subflow) вокруг обзорных Component из `current`-состава (`HAS_COMPONENT.status ∈ {active, deprecated}`); приложение **без** `ApplicationVersion(current)` или с **пустым** `current`-составом **не** показывается. `Component` на холсте — только из такого состава приложений **этого** юнита как **обзорный** `Component` (id = Component, без «Имя · версия»); draft-only, unactive-only и компоненты вне `current` приложений юнита (в т.ч. только в чужих приложениях) **не** показываются. Плоских Component у `Team` **нет** — все видимые компоненты только внутри контейнеров Application. Один Component в нескольких приложениях → копии внутри каждого контейнера с меткой **`duplicate`**; ребро `MAINTAINS` ведёт к обеим копиям. Виртуальные рёбра **`USES`** (`Feature → Component`) строятся на SPA из `USES_COMPONENT_VERSION` (FV ∈ {`draft`,`active`,`deprecated`}, CV ∈ {`active`,`deprecated`} и в `current`-составе юнита); лейбл ребра — `USES`; при нескольких `applicationId` — отдельное ребро к нужной копии. Рёбра **`DEPENDS_ON`** на unit **не** показываются; внешний контекст и чужие юниты **не** показываются (детализация — диаграммы команды, услуги, cross-unit, application-version и др.). Фильтр состава применяется и в API, и на SPA (страховка).
- Если у Feature **единственная** версия и она `draft` — draft-информация на **ноде** Feature; на ребре `USES` draft-приписок нет. Если есть и `active`/`deprecated`, и `draft` — ребро обычное `USES` без draft-пометки.
- Заголовок страницы: **`Юнит {name}`** (`{name}` — имя юнита из ответа API), а не общее слово «Diagrams» из пункта меню.
- В **легенде** — блок **«Фильтры на диаграмме»**: аккордеоны по экземплярам (Команды / Компоненты / Услуги / Функционалы / Приложения; пустые секции не показываются). Каталог id+имя фиксируется **один раз** из первого ответа `GET` графа юнита (после обзорной проекции и фильтра current-состава); при скрытии сущности она **остаётся** в списке. Шапка секции — select all / deselect all (indeterminate при частичном выборе; клик по indeterminate включает все). Поиск по имени — если в секции **> 10** записей. Секции свёрнуты по умолчанию; можно открыть несколько. Скрытие **только на UI** (без повторного API): пересчёт видимого подграфа и ELK из уже загруженного base. Фильтры независимы, кроме: выключенное **приложение** скрывает компоненты **внутри него** (`parentId`). Выключение компонента в списке скрывает **все** его копии. Пустые Application после фильтра убираются. Рёбра рисуются **только** если оба конца есть среди видимых нод. Не относится к `/units/:id/diagram/cross-unit`.
- Контекстное меню **не** содержит **«Показать влияние»**; impact с этой диаграммы не вызывается. Пункт **«Открыть в списке»** — **см. §5.2.1**.
- Переключатель **«Юнит» / «Между юнитами»** размещается **в панели легенды** (сверху). Переход на cross-unit ведёт на **`/units/:id/diagram/cross-unit`** (тот же `:id`, что в маршруте диаграммы юнита); возврат вкладкой **«Юнит»** — на `/units/:id/diagram` (см. [frontend-routes.md](./frontend-routes.md)). На cross-unit ноды `Unit` **сохраняются** ([§5.5](#55-обзорная-cross-unit-диаграмма-diagramscross-unit)).
- Действия с данными юнита на этой странице (создание компонента и др. через модалки) привязаны к **`:id` в маршруте**, даже если в шапке выбран другой юнит.
- Масштаб и смещение холста при переключении фильтров экземпляров и при смене LR/TB **не** сбрасываются программной подгонкой вида.

### 5.3.0. Hover-подсветка связей

- Триггер: `mouseEnter` / `mouseLeave` по ноде на холсте (без отдельной кнопки и без dimming остального графа).
- Область (эта версия): **`/units/:id/diagram`** и **обзор** `/units/:id/diagram/cross-unit` (см. §5.5); прочие диаграммы и drill-down cross-unit — **не** применяют это правило.
- Алгоритм: **все инцидентные видимые рёбра 1-го уровня** (нода — `source` или `target`) **+ свой структурный подъём**; цепочки соседей **не** разворачиваются. Скрытые (`hidden`) ноды и рёбра не входят в путь. Нода `Unit` на unit-холсте отсутствует и **не** акцентируется.
- **Duplicate** Component: только hovered-копия и её контейнер Application (`parentId`); соседние копии того же Component в других приложениях **не** подсвечиваются.
- Визуал пути: цвет `#1677ff`; рёбра — `strokeWidth` `3px`; ноды — обводка `2px` (остальной граф без изменения opacity).

**Состав пути на unit-диаграмме** (по типу hovered-ноды; рёбра USES на холсте — `relationshipType = USES_COMPONENT_VERSION`):

| Hover | В путь |
|--------|--------|
| **Component** | инцидентные `USES_COMPONENT_VERSION` / `MAINTAINS` (Feature, Team); подъём Feature→Service по `AGGREGATES`; свой контейнер Application |
| **Feature** | инцидентные `USES_COMPONENT_VERSION` и `AGGREGATES`←Service; контейнеры Application у связанных Component |
| **Service** | только инцидентные `AGGREGATES`→Feature (без спуска к Component) |
| **Team** | инцидентные `MAINTAINS`→Component + контейнеры Application этих Component |
| **Application** (контейнер) | дочерние Component (`parentId`) + Team/Feature по их инцидентным `MAINTAINS` / `USES_COMPONENT_VERSION` |

### 5.3.1. Диаграмма команды (`/teams/:id/diagram`)

- Обзорная диаграмма (§5.0): данные `GET /api/diagrams/team/:id` ([diagrams-api.md](../diagrams-api.md)).
- Нода `Team` в ответе API есть (имя для заголовка), на холсте **не** показывается; рёбра **`MAINTAINS`** от этой команды на холсте **не** рисуются. Компоненты команды — с проекцией CV→`Component` «Имя · версия» внутри контейнеров Application; связанные **`Feature`**, **`Service`**, **`Application`** — только через **продовые** версии компонентов (`ComponentVersion` в статусах **`active`** / **`deprecated`**) и опубликованные линии фич / текущий релиз приложения, как в API.
- Заголовок страницы: **`Команда {name}`** (`{name}` — имя команды из ответа API).
- На ноде `Feature` показывается только линия **`active`** (`actualVersion`); поля / бейджи `draft` / `deprecated` / `unactive` на ноде **не** показываются.
- UI-only чекбокс **«Только код»** в легенде (отдельный блок **над** аккордеонами; по умолчанию **выкл.**). При включении на холсте остаются только `Application` (контейнеры), `Component` внутри них и рёбра **`DEPENDS_ON`**; ноды `Service` / `Feature` и инцидентные рёбра (`AGGREGATES`, `USES`, …) скрываются. Скрытие **только на UI** (без повторного API и без query в URL); масштаб и смещение холста при переключении **не** сбрасываются (`fitView` не вызывается). При смене `:id` команды чекбокс **сбрасывается в выкл.**
- Легенда (`getLegend`): аккордеоны **Приложения** / **Функционалы** / **Услуги** (без юнитов и команд); при включённом **«Только код»** аккордеоны **Функционалы** и **Услуги** **скрыты** (остаётся только **Приложения**).
- Рёбра **`DEPENDS_ON`** — только **внутренние** (оба конца в составе видимых приложений команды); внешний контекст соседей не подтягивается.
- Контекстное меню нод: **«Показать влияние»** доступно (как на прочих универсальных диаграммах, §5.2), режим impact для команды — **`on-prod`** (согласовано с production-проекцией графа). Пункт **«Открыть в списке»** — **см. §5.2.1**.
- Контекстное меню холста: доступен пункт **«Создать компонент»**; пункт **«Добавить компонент»** (выбор существующей `ComponentVersion` для работы с `FeatureVersion(draft)`) на диаграмме команды **не** показывается.
- При создании компонента команда-владелец берётся по умолчанию из `:id` в маршруте (`teamId`); поле выбора команды в форме **не отображается**.

### 5.3.2. Состав версии приложения (`/applications/:id/versions/:version/diagram`)

- Экран **не** является диаграммой: read-only таблица состава `HAS_COMPONENT` выбранной `ApplicationVersion`.
- Данные: SPA резолвит `:version` → id версии (`current` = статус `current`; иначе совпадение `ApplicationVersion.version`), затем `GET /api/application-versions/:id/composition` (контракт — Swagger `/api/docs`). Литерал **`latest`**, отсутствие целевой версии / нет `current` при запросе `current` → **404**.
- `/applications/:id/diagram` → редирект на `/applications/:id/versions/current/diagram`.
- Колонки: **название компонента** (`Component.name`), **команда** (`Team` через `MAINTAINS`, иначе **`—`**), **версия** (`ComponentVersion.version`), **статус в версии** (`HAS_COMPONENT.status` = `active` | `deprecated`).
- При просмотре **`current`**: у названия компонента в строке с `HAS_COMPONENT.status = deprecated` — жёлтый треугольник (**см. §7.4**); tooltip: **«Устаревшая версия (deprecated)»**. При просмотре **`previous`**: жёлтый треугольник у названия, если глобальный `componentVersionStatus = unactive` **или** в снимке `HAS_COMPONENT.status = deprecated` (**см. §7.4** п.4); клик → модалка (§8.5).
- Фильтры (как визард §4): имя (`Input`, substring) и команда (`Select`, `allowClear`, «Все команды»).
- Мутации состава — только визард §4. Создание **`DEPENDS_ON`** с этого маршрута **не** выполняется.
- На списке `/applications` кнопка **«Состав»** ведёт на `/applications/:id/versions/current/diagram`.

### 5.4. Диаграмма версии функционала (`/feature-versions/:id/diagram`)

- Данные `GET /api/diagrams/feature-version/:id` ([diagrams-api.md](../diagrams-api.md)). Контекст — конкретный `FeatureVersion`. Каждая `ComponentVersion` из состава проецируется в ноду **`Component` «Имя · версия»** (или **`dependency`**, если `Component.type = dependency`) внутри контейнера Application (§5 subflow; membership по `HAS_COMPONENT` и `USES.applicationId`); два CV одного Component → две копии. Плоский component/dependency без контейнера на холсте **не** допускается для новых добавлений; у уже существующих плоских артефактов действия на ноде **блокируются**.
- **Версия приложения в рамке:** для **`draft`** — `ApplicationVersion(current)` (как на обзорных диаграммах). Для **опубликованной** FV — снимок **`PINNED_TO_APPLICATION_VERSION`** на момент `draft → active` ([spec.md §6](../spec.md)): при переключении версий в легенде меняется подпись контейнера «Имя · версия» и `HAS_COMPONENT` от pinned AV. Если pin для приложения отсутствует (аномалия данных) — контейнер Application **без** «· version»; **`current` не подставляется**.
- На графе: команды, приложения, рёбра **`DEPENDS_ON`**. Ноды **Feature**, **FeatureVersion** и **Service** **не показываются**. Нода **`Unit` на холсте всегда скрыта** (в т.ч. при cross-unit). Ребро **`STAKEHOLDER`** `Unit → Feature` **не показывается**, если функционал уже виден через услуги в данных API.
- **Cross-unit на холсте.** UI-only чекбокс **«Связь с другим юнитом»** (default **выкл.**). При **выкл.**: чужие Application / CV и cross-unit `DEPENDS_ON` (разные `unitId` у концов) **скрыты**; на **локальной** ноде-потребителе исходящего cross-unit ребра — маркер **`?`** (§7.4) рядом с deprecated при наличии. При **вкл.**: на холсте появляются чужие **Application** и **Component** («Имя · версия») и ребро `DEPENDS_ON`; чужие **`Unit` / `Team` / `Feature` / `Service` не рисуются** (только в tooltip у `?`); маркер **`?`** — только на **чужой** ноде Component (на локальных нет). Tooltip у `?`: текстом **Юнит**, **Команда**, **Приложение**, **Компонент**, **Фича**, **Сервис** (отсутствующее — `—`); при **выкл.** и нескольких исходящих cross-unit с одной локальной ноды значения в поле могут быть **списком** (уникальные имена через запятую). Same-unit `DEPENDS_ON` видны **всегда**. Скрытие cross-unit — **только на UI** (без повторного API); при переключении версий в легенде той же сессии диаграммы фичи чекбокс **сохраняется**; сброс в **выкл.** — при уходе с диаграммы версии фичи (и при повторном входе); `fitView` при переключении **не** вызывается.
- Заголовок: **`Фича {name} {version} ({status})`**.
- Вход с экрана функционалов / старого `/features/:id/diagram`: открывается **`active`**, если есть; иначе версия с максимальным `versionNumber`. Легенда: блок **«Версии функционала»** (draft первым в списке); ниже — отдельный блок с тогглом **«Граф» / «Таблица»** и UI-only чекбоксами **«Команды»**, **«Связь с другим юнитом»** и **«Сравнить с предыдущей»** (без аккордеона / instance-списка). Чекбоксов типов приложений / функционалов / услуг **нет**. Чекбокс **«Команды»** всегда показывается и по умолчанию **включён** (даже если в графе нет нод `Team`); при выключении скрываются только ноды `Team` и рёбра `MAINTAINS` (компоненты, Application, `DEPENDS_ON` остаются); рёбра к отсутствующей ноде (в т.ч. `HAS_TEAM`) не рисуются. Скрытие **только на UI** (без повторного API); масштаб и смещение холста при переключении **не** сбрасываются.

#### Табличный вид

- В блоке фильтров легенды — тоггл **«Граф» / «Таблица»** (как scope-тогглы услуги). По умолчанию открыт вид графа. Выбранный вид занимает ту же область. Данные те же, что у холста (`GET /api/diagrams/feature-version/:id`); отдельного маршрута нет.
- **Свой список.** Группа — контейнер Application; заголовок группы — подпись рамки («Имя · версия»; без pin — без «· version», правило рамки выше). Колонки строки: **компонент** (`Component.name`), **версия** (`ComponentVersion.version`), **команда**. Колонок **«Фича»** и **«Услуга»** нет. Один и тот же компонент в двух приложениях — две строки. Рёбра **`DEPENDS_ON`** в таблице не показываются.
- **Команда:** нет ребра `MAINTAINS` — **`—`**. Несколько команд — уникальные имена через запятую.
- В табличном виде чекбокс **«Команды»** включён и недоступен для снятия. На виде графа его можно выключать (правило легенды выше). **«Связь с другим юнитом»** и **«Сравнить с предыдущей»** в таблице работают по тем же правилам, что на холсте. Строка, которая есть в открытой версии и нет у предшественника, — зелёная; строка, которая есть у предшественника и нет в открытой, — красная. Ключ строки — **`componentVersionId` + `applicationId`** (**см.** [сравнение](#сравнение-с-предыдущей-версией)). Пока сравнение включено, таблица только для просмотра.
- **Чужой юнит.** Пока **«Связь с другим юнитом»** выключена, чужих блоков нет. Когда включена: под разделителем с названием юнита для каждой пары поставщика (`service_id` + `feature_id` контекста `DEPENDS_ON`, [spec.md §7.2](../spec.md)) один раз поля **«Услуга»** и **«Фича»**, ниже свой список с теми же колонками и группами приложений. Несколько пар — несколько таких блоков. У своего списка этих полей нет.
- **Действия.** Колонка **«Действия»**; в строке отдельные кнопки с теми же пунктами и условиями, что у правого клика по ноде на холсте: **«Открыть в списке»**, а для `draft` — **«Добавить связь»**, **«Связь с другим юнитом»**, **«Поднять версию»**, **«Исключить из фичи»**. **«Показать влияние»** в таблице нет. Удаление **`DEPENDS_ON`** — действие ребра, в строке его нет. Над таблицей в `draft`, пока сравнение выключено: **«Создать компонент»** и **«Добавить компонент»**. Пока сравнение включено, кнопки состава и **«Открыть в списке»** скрыты, как на холсте. На опубликованной линии состав не меняется.

- Для `draft`: в меню холста доступны **«Создать компонент»** и **«Добавить компонент»**. Оба сценария требуют Application: выбрать существующее или **создать** (та же форма, что на вкладке Applications) и сразу привязать (`applicationId`). Автовыбора с пропуском шага **нет**: после выбора CV пользователь всегда видит шаг приложения. Select приложений юнита **disabled**, если вариантов **0 или 1** (при одном значение предзаполнено); кнопка **«Создать приложение»** **всегда** видна и активна (то же правило в модалке привязки приложения, в форме Application при создании компонента и при создании `DEPENDS_ON`). «Добавить компонент» вызывает `POST /api/feature-versions/bind-component-versions` ([diagrams-frontend](../diagrams-frontend.md)). Создание `DEPENDS_ON` / cross-unit Application **не** создаёт и не выбирает App отдельно — см. [§9](#9-зависимости-depends_on).
- Для `draft`: ПКМ по компоненту внутри Application — **«Добавить связь»** (same-unit `DEPENDS_ON`, выбор provider из состава draft), **«Связь с другим юнитом»**, **«Исключить из фичи»** (снятие `USES_COMPONENT_VERSION` через `bind-component-versions` `remove`), **«Поднять версию»** (автоматизация замены CV в этом `applicationId`: создать/выбрать более новую CV и переключить `USES`, sync исходящих `DEPENDS_ON` для этого app — `POST /api/feature-versions/raise-component-version`, контракт в Swagger `/api/docs`, [spec.md §6](../spec.md)). После публикации draft → `active` исключённая привязка **не** наследуется в следующие draft ([spec.md §6](../spec.md)).
- Для `draft`: ПКМ по **видимому** ребру **`DEPENDS_ON`** — **«Удалить связь»** (confirm → physical delete копии с `consumerFeatureVersionId` = этот draft) — [§9.4](#94-удаление-depends_on). Cross-unit ребро удаляемо, только если оно видно (чекбокс **«Связь с другим юнитом»** включён). В режиме сравнения и на опубликованной FV пункта нет.
- **«Поднять версию»** (только `FeatureVersion(draft)`, нода CV внутри Application, не flat; **скрыт**, если статус кликнутой CV уже `draft`; в режиме сравнения — скрыт). Кандидаты: CV того же `Component` с `versionNumber` строго больше текущей и статусом `draft | active | deprecated`. **0** кандидатов — сразу создать новую `draft` CV (номер по умолчанию) и подставить; **1** — подставить сразу; **≥2** — модалка выбора. Заменяется только `USES` с `applicationId` кликнутой ноды; привязки того же компонента в других приложениях draft **не** трогаются. Исходящие `DEPENDS_ON` у целевой CV для этого `consumerApplicationId` синхронизируются с набором у исходной CV (лишние снимаются, недостающие добавляются; `consumerFeatureVersionId` = текущий draft); входящие `DEPENDS_ON` этого draft на исходную CV с тем же `providerApplicationId` переносятся на целевую CV. Дальше пользователь может поправить связи вручную. Операция **не** пишет `HAS_COMPONENT` и **не** меняет `readyToProduction` / `PINNED_*` иначе, чем после ручной замены USES.
- Для опубликованной линии (`active` / `deprecated` / `unactive`): меню холста без create/add; состав `USES` не меняется; пунктов «Добавить связь» / «Поднять версию» / «Исключить из фичи» / «Связь с другим юнитом» нет.
- Для `draft`: также доступны impact и кнопка **«Проверить готовность»** ([§7.2](#72-readytoproduction-на-диаграмме)); визуальный индикатор на ноде не используется. В режиме сравнения ([ниже](#сравнение-с-предыдущей-версией)) ready и impact **скрыты**. Пункт **«Открыть в списке»** — **см. §5.2.1** (в сравнении скрыт).
- Создание / удаление **`DEPENDS_ON`**: меню **«Добавить связь»** / соединение handles / ПКМ по ребру **«Удалить связь»** на draft — см. [§9](#9-зависимости-depends_on).

**Сравнение с предыдущей версией**

- UI-only чекбокс **«Сравнить с предыдущей»** в блоке легенды (рядом с «Команды»). По умолчанию **выключен**. Поле `inheritedFromId` приходит в элементе ответа `POST /api/feature-versions` (контракт — Swagger `/api/docs`): `uuid` непосредственного предшественника по **`INHERITED`**, либо **`null`**. Если `inheritedFromId = null` — чекбокс **disabled**.
- Пара сравнения: открытая версия `:id` и её непосредственный предшественник по `INHERITED`. Данные — два запроса `GET /api/diagrams/feature-version/...`; diff на клиенте ([diagrams-frontend.md](../diagrams-frontend.md)).
- Пока сравнение **включено**, заголовок страницы: **`Фича {name} · сравнение {version} ({status}) с {prevVersion} ({prevStatus})`**, где `{version}` / `{status}` — открытая (выбранная) версия, `{prevVersion}` / `{prevStatus}` — предшественник по `INHERITED` (локализованные статусы). Вне сравнения заголовок без суффикса (§5.4 выше).
- На одном холсте — объединение графов. **Зелёный** — элемент есть в открытой версии и нет у предшественника; **красный** — есть у предшественника и нет в открытой. Неизменённые ноды/рёбра сохраняют статусную окраску ([§7.4](#74-цветовая-кодировка-статусов)); у неизменённых `deprecated` сохраняется жёлтый треугольник (не жёлтая заливка). У added/removed статусная палитра на время сравнения **не** применяется (полная заливка цветом diff).
- Ключ строки состава: **`componentVersionId` + `applicationId`** (`USES_COMPONENT_VERSION`). Ключ `DEPENDS_ON`: пара концов **`ComponentVersion → ComponentVersion`** (контекст на ребре в ключ **не** входит).
- Ноды компонентов красятся **только** при изменении состава (`USES`); концы неизменённых компонентов у добавленных/удалённых `DEPENDS_ON` **не** красятся (меняется только ребро).
- Контейнер **`Application`** и нода **`Unit`**: diff-цвет **только** если сущности не было в одной из двух версий (появилась или удалена целиком). Ноды **`Team`** и рёбра **`MAINTAINS`** / **`HAS_TEAM`** diff-цветом **не** красятся.
- Пока сравнение **включено**: холст **read-only** (даже для `draft` — без create/add/`DEPENDS_ON`/исключения); кнопка **«Проверить готовность»**, пункты impact (**«Показать влияние»** / сброс) и **«Открыть в списке»** (§5.2.1) **скрыты**. Переключение «Команды» и «Связь с другим юнитом» остаётся; `fitView` при вкл./выкл. сравнения **не** выполняется. При переключении версий в легенде той же сессии диаграммы фичи состояние **«Команды»**, **«Связь с другим юнитом»** и **«Сравнить с предыдущей»** **сохраняется** (если у новой версии нет `inheritedFromId` — сравнение выключается). Сброс к defaults — при уходе с диаграммы версии фичи.

**Отображение зависимостей**

- Отображаются связи `DEPENDS_ON` для CV из состава (`USES_COMPONENT_VERSION`), с фильтрацией по контексту текущей `FeatureVersion` ([spec.md §6](../spec.md)). Same-unit рёбра — всегда; cross-unit — только при включённом чекбоксе **«Связь с другим юнитом»** (§5.4 выше).

### 5.5. Обзорная cross-unit диаграмма (`/units/:id/diagram/cross-unit`)

- Центр cross-unit — `:id` в `/units/:id/diagram/cross-unit`; fallback-логика описана в [frontend-routes.md](./frontend-routes.md).
- На графе показываются **только** центральный юнит и **соседние** юниты с cross-unit связью по `DEPENDS_ON` между `ComponentVersion` (у **компонента-поставщика** `Component.isPublic`, см. [spec.md §8](../spec.md)); остальные юниты не отображаются. Контейнеры Application на **обзоре** не используются (в отличие от drill-down bridge).
- Заголовок страницы: **`Юнит {name} (связи)`**, где `{name}` относится к **центральному** юниту (из ответа графа); при открытой детализации моста (drill-down) заголовок **не** меняется.
- Синтетические мосты **`CROSS_UNIT_LINK`** — только между **центральным** юнитом и каждым соседом (звезда). Рёбра между двумя соседями без участия центра **не** показываются.
- Визуализация моста — **ребро между нодами `Unit`**. Физического ребра `Unit → Unit` в модели нет; связность вычисляется по `DEPENDS_ON` между `ComponentVersion` разных юнитов ([spec.md §8.0](../spec.md)).
- Hover-подсветка (§5.3.0) на **обзоре**: при наведении на `Unit` подсвечиваются инцидентные `CROSS_UNIT_LINK` и соседние `Unit`. На холсте **drill-down** (оверлей) hover-подсветка **не** применяется.
- Раскрытие (drill-down): при выборе моста — детализация до **команд**, **сервисов**, **фич**, **приложений**, **компонентов** (и версий, нужных для связей) с обеих сторон. Детализация отображается **вторым холстом поверх** обзорной диаграммы (оверлей); закрытие — кнопка **«закрыть»** (крестик) в **правом верхнем углу** оверлея. Начальная подгонка вида на обоих холстах — стандартная для `@xyflow/react` (`fitView` при отрисовке), без принудительного смещения камеры при последующих изменениях состава нод. На обзоре и в drill-down ПКМ **«Открыть в списке»** — **см. §5.2.1** (только ноды юнита шапки).
- **Контейнеры Unit на bridge (только SPA).** Оба `Unit` пары — рамки `group` (тот же `GroupNode`, что у Application). Внутри каждого Unit **плоско** лежат `Team`, `Service`, `Feature`, `Application`; компоненты — **только** внутри `Application` (после Application-grouping). `Component` без Application-membership на холст **не** попадает. Принадлежность к Unit: `data.unitId`, иначе fallback по рёбрам `HAS_TEAM` / `PROVIDES` / `OWNS` к одному из двух Unit пары; если не сопоставилось — нода остаётся вне контейнеров Unit. Рёбра `HAS_TEAM` / `PROVIDES` / `OWNS` на холсте **не** рисуются (вложенность уже через `parentId`); `AGGREGATES` / `MAINTAINS` / `USES` / `DEPENDS_ON` остаются. Заголовок рамки Unit — только **`{name}`**; цвет рамки — **HSL** из FNV-хеша **`data.unitId`** (`hue = hash % 360`, фиксированные S/L; один юнит на разных мостах одного цвета; цвета Unit ≠ бирюза Application). В легенде **под** переключателем «Юнит» / «Между юнитами» — UI-only чекбоксы **«Команды»** (default **вкл.**) и **«Только код»** (default **выкл.**; при вкл. скрывает `Service` / `Feature`); блок фильтров **виден только** когда открыт drill-down моста; сброс при открытии/закрытии моста; фильтры применяются **после** Application/Unit grouping (компоненты в App не пропадают); без повторного API. Контракт `GET /api/units/:id/diagram/cross-unit/bridge/...` **не** меняется.
- **Пример.** UnitA и UnitB на bridge: внутри A — TeamA, ServiceA, FeatureA, ApplicationA с ComponentA; внутри B — симметрично. Ребро `DEPENDS_ON` идёт между ComponentA и ComponentB (через границы Unit). Рёбер `OWNS` / `HAS_TEAM` / `PROVIDES` на холсте нет.
- Переключатель **«Юнит» / «Между юнитами»** — в панели легенды слева (как на диаграмме юнита, §5.3); точные правила перехода и fallback для вкладки «Юнит» описаны в [frontend-routes.md](./frontend-routes.md).
- Демо-данные с cross-unit мостами: [`scripts/cypher/seed.cypher`](../../scripts/cypher/seed.cypher) (CoolUnit ↔ CoolUnit2); на обзоре видна только **звезда** от **центрального** юнита.

### 5.6. Диаграмма сервиса

- Отображает функционалы, входящие в услугу (рёбра `AGGREGATES`).
- В **режиме `on-prod`** (по умолчанию): только активные рёбра (без `deleted: true`); данные с API без `?projection=draft`.
- В **режиме `draft`**: query **`?projection=draft`** — включая снятые функционалы (с `deleted: true`) для полноты картины.
- Управление `AGGREGATES` (добавление/снятие функционала): доступно **и** на диаграмме, **и** на странице услуги (§6).
- ПКМ **«Открыть в списке»** — **см. §5.2.1** (в т.ч. на `/services/:id/diagram/integrations`).

### 5.7. Экспорт в Mermaid

- На **всех** диаграммах-холстах (`unit`, `team`, `service` / integrations, `feature-version`, `component`, `cross-unit` overview и bridge) в `Panel` рядом с React Flow **Controls** — кнопка с иконкой Mermaid (tooltip **«Скопировать Mermaid»**). Таблица состава приложения (§5.3.2) кнопку **не** показывает.
- По клику клиент собирает текст из **видимого** подграфа (`hidden !== true`) и текущей ориентации холста (`TB` / `LR`) → `navigator.clipboard.writeText`. Отдельного API нет.
- Формат: `flowchart TB|LR`; контейнеры (`type: group`, в т.ч. Application / Unit на bridge) → `subgraph`; подписи нод как на холсте (`captionWithOptionalVersion` / `groupNodeCaption`); маркеры deprecated / `duplicate` / `?` **не** включаются; рёбра с подписью `relationshipType`.
- Пустой видимый граф: в буфер кладётся заглушка — только строка `flowchart TB` или `flowchart LR`.
- Toast: успех — **«Mermaid-диаграмма скопирована»**; ошибка clipboard — **«Не удалось скопировать mermaid-диаграмму»** (§8.1).
- Копирование **не** пишет в `sessionStorage` страницы Tools; пользователь вставляет текст вручную (§10).

## 6. Управление составом услуги (AGGREGATES)

- Добавление функционала в услугу и снятие функционала из услуги доступно **на странице услуги** и **на диаграмме услуги**.
- Снятие функционала: soft-delete — на ребре выставляется `deleted: true` ([spec.md §2.1](../spec.md)); при снятии допускается модалка с опциональным полем «причина» (текст сохраняется на ребре в Neo4j как `deleted_reason`; см. [aggregates-api.md](../aggregates-api.md)).
- Повторное добавление: создаётся новое ребро `AGGREGATES`; прежнее с `deleted: true` сохраняется (история).

## 7. Индикаторы и статусы

### 7.1. `readyToProduction` на странице версий

- На странице `/features/:id`: рядом с `FeatureVersion(draft)` показывается бейдж готовности (например «Готов к публикации» / «Не готов»).
- Пустой черновик (нет привязок `USES_COMPONENT_VERSION`) всегда показывает «Не готов».
- Значение индикатора берётся из данных доменной модели.
- Канонические бизнес-правила расчёта `readyToProduction` и `canAutoActive` описаны в [spec.md §6](../spec.md).
- Кнопка перехода `draft → active` (**«Активировать»**) **недоступна**, если у черновика нет связанных компонентов.
- Кнопка перехода `active → unactive` (**«Деактивировать»**) доступна для опубликованной линии; перед переходом — подтверждение с impact (§8.2). Ручные переходы `active → draft` и `unactive → active` в таблице **не** показываются.

### 7.2. `readyToProduction` на диаграмме

- На версионной диаграмме фичи (`/feature-versions/:id/diagram`) для `draft` доступна кнопка **«Проверить готовность»**; отдельный визуальный индикатор на ноде не показывается (ноды Feature / FeatureVersion на холсте нет).
- Канонические бизнес-правила расчёта `readyToProduction` и `canAutoActive` описаны в [spec.md §6](../spec.md).

### 7.3. Обновление индикатора в UI

- **Event-driven:** UI отражает актуальное значение `readyToProduction` после событий изменения статусов и последующей синхронизации данных.
- **On-demand:** пользователь может запустить ручную проверку готовности (кнопка **«Проверить готовность»** на `/features/:id` и на `/feature-versions/:id/diagram`), после чего UI обновляет отображаемый статус.
- Результат проверки (toast и модалка **взаимоисключающи** для успешного ответа check-ready):
  - toast **`success`** — версия автоматически опубликована или черновик готов к публикации; модалка **не** открывается;
  - toast **`warning`** — пустой состав (`reason = no_component_bindings` / нет `USES`): «Нет связанных компонентов»; модалка **не** открывается;
  - toast **`error`** — сбой запроса (в т.ч. попытка публикации пустого черновика → сообщение «Нет связанных компонентов»);
  - модалка **«Проверка готовности функционала»** — только если есть хотя бы одна привязка с `ready === false` в `bindings[]` и/или `crossUnitBindings[]`; toast по этому же ответу **не** показывать. В **первой** таблице только привязки `USES` с `ready === false`: **приложение** (текст `applicationName`, ссылка `/applications?highlight=:applicationId&ctx.unitId=:unitId`), **компонент** (текст `componentName`, ссылка `/components?highlight=:componentId&ctx.unitId=:unitId`), **версия** (текст `componentVersion` — цель `USES_COMPONENT_VERSION` проверяемого черновика, без ссылки), **статус в релизе**, **причина**. В `highlight` — только `applicationId` / `componentId`, не `componentVersionId`; `unitId` из строки уходит в `ctx.unitId`. На списке: подсветка строки, пока query в URL; после загрузки — `scrollIntoView`. Если строки нет и `ctx.unitId` ≠ текущий UnitContext — toast и переход на `/units?highlight=:unitId`; если юнит совпадает (или `ctx.unitId` нет), а строки нет — toast. На **`/components`**: если id есть в **загруженных** данных списка, но скрыт **клиентскими фильтрами** (§3.1) — это **не** mismatch: без toast и без подсветки (остальные видимые строки остаются).
  - Ниже первой таблицы — заголовок **«Другой юнит»** и **вторая** таблица с теми же колонками по `crossUnitBindings[]` с `ready === false` (исходящие cross-unit `DEPENDS_ON`, [spec.md §6](../spec.md)); ссылки используют `unitId` стороны поставщика. Если неготовых внешних строк нет — заголовок и вторую таблицу **не показывать**.
- Контракт ответа: `POST /api/feature-versions/check-ready` (Swagger `/api/docs`). Логика проверки и автоперехода — [spec.md §6](../spec.md).

### 7.4. Цветовая кодировка статусов

- `draft` — нейтральный/серый (не на проде).
- `active` / `current` — зелёный (на проде / текущий).
- `deprecated` — **на проде**; в **chip/бейдже** статуса — жёлтый/оранжевый (`warning`); на **ноде диаграммы** заливка как у `active` / `current` (зелёный), без жёлтой заливки ноды — отличие дополнительно **жёлтым треугольником** (иконка warning, цвет **`#FAAD14`**). Tooltip у маркера сущности: **«Устаревшая версия (deprecated)»**.
- `unactive` (для **`ComponentVersion`** / **`FeatureVersion`**) — тусклый/серый (история / вне текущего прод-релиза); у **`ComponentVersion`** дополнительно **тот же** жёлтый треугольник (`#FAAD14`), если версия видна в контексте экрана (см. ниже). Tooltip: **«Версия снята с прода (unactive)»**.
- `previous` (для **`ApplicationVersion`**) — тусклый/серый.
- Жёлтый треугольник у **`ComponentVersion`**: (1) прикладной `HAS_COMPONENT.status = deprecated` в контейнере / строке `ApplicationVersion(current)`; (2) глобальный статус `unactive` при `USES` на диаграмме версии фичи (в т.ч. без `HAS_COMPONENT` в current); (3) строка `unactive` в таблице версий компонента; (4) CV в составе `previous`, ставшая глобально `unactive` (или с `HAS_COMPONENT.status = deprecated` в снимке). Клик → модалка (§8.5). На списке **`/applications`** — **один** треугольник у названия при `hasStatusWarning` (§3.1); tooltip: **«Есть компоненты с предупреждением (deprecated / unactive)»**; клик → §8.5 (шаг 1).
- **Cross-unit hint (`?`)** — на `/feature-versions/:id/diagram` в правом верхнем углу ноды CV (рядом с треугольником статуса, если оба нужны): знак вопроса; tooltip — **Юнит** / **Команда** / **Приложение** / **Компонент** / **Фича** / **Сервис** текстом (поля могут быть списком при нескольких remote, [§5.4](#54-диаграмма-версии-функционала-diagramsfeature-versionid)).

**Пример.** Приложение A, `ApplicationVersion(current)` содержит CV₁ с `HAS_COMPONENT.status = active` и CV₂ с `status = deprecated`: на `/applications` — треугольник у названия A; в составе `…/versions/current/diagram` и на шаге 1 визарда релиза — треугольник у названия строки CV₂; на диаграммах team / feature-version в контейнере A(`current`) — треугольник у ноды CV₂. Нода CV с `USES` на `unactive` без `HAS_COMPONENT` в current — треугольник есть; клик открывает §8.5. Обзорная диаграмма юнита — маркеров нет.

## 8. Уведомления и предупреждения

### 8.1. Тосты (неблокирующие)

- Используются для неблокирующей обратной связи после CRUD и операций на диаграммах.
- Page-level ошибки на списках, страницах версий, диаграммах и в визарде релиза (сбой загрузки, отказ операции, «нет данных» для отображения) показываются **только** через toast `error`; постоянные баннеры над таблицей или холстом **не** используются. Исключение: пустой результат **клиентских фильтров** на `/components` (§3.1) — стандартное empty-состояние таблицы Ant Design **без** toast.
- Mermaid (§5.7, §10): **«Mermaid-диаграмма скопирована»** / **«Не удалось скопировать mermaid-диаграмму»**; при ошибке «Вставить из буфера» — **«Не удалось вставить из буфера»** (успешная вставка — **без** toast).
- Реализуются через **`App.useApp()`** и **`notification`** из Ant Design ([Notification](https://ant.design/components/notification/)).

### 8.2. Критичные модалки (блокирующие, с обязательным подтверждением)

- Для рискованных переходов `FeatureVersion` используется блокирующее подтверждение с impact-снимком до отправки transition.
- Реализуется отдельным компонентом на базе **`Modal`** из Ant Design; перед переходом запрашивается impact по API (`GET /api/impact/feature/:id` и др. по контексту).

### 8.3. Предупреждения на диаграммах

- Аномалии production-проекции (`DEPENDS_ON` на нецелевые статусы и другие риск-сочетания) подсвечиваются визуально на графе (стили нод/рёбер в коде диаграммы).

### 8.4. Ошибки внутри модалок

- Ошибки валидации и сбои submit **внутри** `Modal` по-прежнему отображаются через `Alert` (или локальный текст формы) в теле модалки; правило §8.1 про page-level баннеры к ним не применяется.

### 8.5. Модалка предупреждения по deprecated / unactive ComponentVersion

- Точка входа: **клик** по жёлтому треугольнику (§7.4) на всех экранах, где маркер есть.
- Если `componentVersionId` уже известен (нода, строка состава / визарда / таблицы версий) — сразу **шаг 2**.
- На **`/applications`**: `GET /api/applications/:id/status-warning-candidates` (контракт — Swagger `/api/docs`) → **шаг 1** (выбор CV с пометкой `deprecated` | `unactive`); один кандидат — сразу шаг 2.
- **Шаг 2** — `GET /api/component-versions/:id/status-warning` (контракт — Swagger `/api/docs`):
  - **основной блок:** приложения и команды «для уведомления» (только отображение имён; доставка / копирование контактов — вне scope);
  - **свёрнуто** (`Collapse`): взаимодействующие компоненты, фичи, услуги; пустую секцию **не показывать**; если основной блок пуст — текст **«Нет связанных …»** по типу.
- **Приложения:** объединение (1) `consumerApplicationId` / `providerApplicationId` учтённых `DEPENDS_ON`; (2) `Application` с `HAS_COMPONENT` у `current` к выбранной CV и к соседним продовым CV; (3) `USES.applicationId` от FeatureVersion `draft` | `active` | `deprecated` на выбранную CV.
- **Команды:** `MAINTAINS` родительского Component выбранной CV ∪ `MAINTAINS` концов каждого учтённого `DEPENDS_ON` (без дублей).
- **Компоненты (свёрнуто):** соседние `ComponentVersion` по `DEPENDS_ON` в **оба** направления; сосед только со статусом **на проде** (`active` | `deprecated`); cross-unit — с учётом `isPublic` поставщика ([spec.md §8](../spec.md)).
- **Фичи / услуги (свёрнуто):** только от **выбранной** CV — FeatureVersion с `USES` на неё (`draft` | `active` | `deprecated`); услуги — активные `AGGREGATES` к этим Feature (без `deleted: true`).

## 9. Зависимости (DEPENDS_ON)

### 9.0. Отображение направления

- На **всех** диаграммах, где рисуется ребро `DEPENDS_ON`, у ребра видна **стрелка** consumer → provider. Остальные типы рёбер (`USES`, `MAINTAINS`, `AGGREGATES`, `CROSS_UNIT_LINK`, …) **без** стрелок.
- Пара противоположных рёбер `A→B` и `B→A` (два контракта, [spec.md §7](../spec.md)) рисуется как **две отдельные линии**, визуально **разведённые** (смещение), чтобы можно было навести и удалить нужную (§9.4).
- Обратную связь (`B→A` при уже существующей `A→B`) создают **тем же** сценарием §9.1–9.3 с другого конца пары (ПКМ **«Добавить связь»** / drag); отдельного пункта «Создать обратную» **нет**.

### 9.1. Точка входа (создание)

- Инициируется **с диаграммы** версии функционала (`/feature-versions/:id/diagram`): ПКМ **«Добавить связь»** / соединение handles между спроецированными нодами `Component` (id = CV).
- На `FeatureVersion(draft)` при `nodesConnectable` у нод `component` / `dependency` handles показываются всегда (не только при уже существующих рёбрах).
- С экрана состава приложения (§5.3.2) создание `DEPENDS_ON` **недоступно**; same-feature на FV-draft — упрощённый сценарий ниже.

### 9.2. Поиск целевого компонента

- Same-unit из меню: Select provider из CV/`dependency` состава текущего draft (исключая consumer; при нескольких `USES.applicationId` — отдельные строки).
- Drag: оба конца — ноды на холсте (в т.ч. внутри разных Application); модалка подтверждает пару без выбора списка.
- Переключение на **другой юнит** — пункт **«Связь с другим юнитом»** только с ноды компонента **внутри** Application (`USES.applicationId` / контейнер); без привязки к приложению действие недоступно.
- При cross-unit в поиске цели отображаются только те **`ComponentVersion`**, у чьего родительского **`Component`** задано **`isPublic = true`** ([spec.md §8](../spec.md)).
- Ограничения: новые связи на `unactive` запрещены; на `deprecated` — по правилам [spec.md §4.1](../spec.md).

### 9.3. Заполнение контекста

- **Same-unit на `FeatureVersion(draft)`:** модалка показывает только consumer и выбор/подтверждение provider. Поля service / application / feature / featureVersion **в UI не показываются**; контекст формируется системой и уходит в `POST /api/edge/depends-on/from-feature-versions` (один и тот же draft FV на обеих сторонах; `applicationId` из `USES`) — [spec.md §7.2](../spec.md).
- **Cross-unit** с `FeatureVersion(draft)`: `consumerApplicationId` — из ноды входа (в форме **не** показывается). Каскад поставщика: **Unit → Service → Feature → FeatureVersion → Application → ComponentVersion**. Application и CV строятся из `USES` выбранной `FeatureVersion` (не из полного списка Application юнита). На каждом шаге: один вариант — предзаполнить и **disable**; несколько — ручной выбор. Создание Application из диалога связи **запрещено**. Полный контекст на ребре по-прежнему обязателен ([spec.md §7.2](../spec.md)); API тот же `POST /api/edge/depends-on/from-feature-versions`.

### 9.4. Удаление DEPENDS_ON

- Только на `/feature-versions/:id/diagram` при `FeatureVersion(draft)` и **не** в режиме сравнения.
- ПКМ по **видимому** ребру `DEPENDS_ON` → **«Удалить связь»** → confirm Modal → `POST /api/edge/depends-on/delete` с ключом `sourceComponentVersionId`, `targetComponentVersionId`, `consumerFeatureVersionId` (= якорь), `consumerApplicationId`, `providerApplicationId` (контракт — Swagger `/api/docs`).
- При паре `A→B` и `B→A` удаляется **только** выбранная линия (направление); вторая остаётся.
- Удаляется только копия ребра этого draft; рёбра других версий фичи не меняются.
- Same-unit рёбра видны всегда; cross-unit — только при включённом чекбоксе **«Связь с другим юнитом»** (§5.4). Скрытое ребро удалить из UI нельзя.
- На опубликованной FV и для рёбер не-`DEPENDS_ON` пункт меню не показывается.

## 10. Инструменты (Mermaid)

- Пункт верхнего меню **«Инструменты»** (перед **«Справка»**) → подпункт **«Mermaid»** → `/tools/mermaid` ([frontend-routes.md](./frontend-routes.md)).

- Кнопка **«Вставить из буфера»**: читает `navigator.clipboard.readText`; успех — без toast; ошибка — §8.1.
- Кнопка **«Свернуть»** / **«Развернуть»**: прячет/показывает колонку редактора; превью занимает половину ширины или всю. Состояние свёртки при каждом открытии страницы **сбрасывается** (редактор раскрыт).
- Текст textarea восстанавливается из `sessionStorage` (`stellode.tools.mermaid`) при открытии; при изменении снова сохраняется. Копирование с диаграммы (§5.7) в storage **не** пишет.
- Синтаксическая ошибка Mermaid отображается **как у библиотеки Mermaid** (без отдельного кастомного Alert).
